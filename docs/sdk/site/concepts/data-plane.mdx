An agent's documents, its skills, the credentials its tools need, and the sandbox it runs in all
live somewhere. On Agent Workspace that "somewhere" is never a choice the developer makes: the
SDK's vocabulary is files, skills, connectors and runtime profiles, never a bucket, a table, a
key ring or a disk path ([design principle 1](/concepts/design-principles)). It is also never a
choice a fork makes: an operator configures placement once, per deployment, as three profiles —
storage, runtime, identity — and the same images and the same agent definitions run unchanged on
a laptop or on any of the three big clouds ([design principle
2](/concepts/design-principles)). And "managed on your cloud" means native: each store maps to
that cloud's own service, not to an S3-compatible shim wearing a different logo, and a cell in
the table below counts as done only once a live proof exists against the real service ([design
principle 3](/concepts/design-principles)). This page states that contract — what exists today,
cloud by cloud, honestly — and how a file, a skill and a secret actually move through it.

## What the developer sees, and what the operator configures

| The developer sees (`aw.<resource>.*`)                        | The operator configures (once, per deployment)                                    |
| ------------------------------------------------------------- | --------------------------------------------------------------------------------- |
| `files` — documents an agent reads or writes                  | a _storage_ profile: relational database, object store, secret backend            |
| `skills` — reusable instructions and helper files             | the same storage profile's object store                                           |
| `connectors` — MCP servers and the credentials they need      | the same storage profile's secret backend                                         |
| `agents`, `sessions`, `runs`, `people`                        | the platform's own relational store                                               |
| a runtime profile naming a driver, sizing, and network policy | a _runtime_ profile: which sandbox driver is the default, and its connection      |
| an agent's `engine`, and `installed` on `GET /api/engines`    | one runtime image per engine it offers (`AGENT_WORKSPACE_RUNTIME_IMAGE_<ENGINE>`) |

Nothing in the left column names a cloud service. Nothing in the right column is visible to an
agent or to the SDK's types. One rule follows directly and holds regardless of what a future
driver or backend adds: **your own databases and document systems reach an agent only as an MCP
connector or as uploaded files — never through the platform's stores.** The platform's PostgreSQL
holds Agent Workspace's own rows (workspaces, agents, runs); its object store holds what you
uploaded or a skill's files; neither is a general-purpose data store your product's other systems
read or write directly.

## The contract

Four concerns, three clouds, one _Today_ column stating what is actually implemented and proven,
never what is planned. A "✅" cell means the cloud's own managed service works today; "partial"
means a workaround exists but is not the native service; "✗" means nothing exists for that cell
yet. Every claim below is backed by the file named after it — see [the migration
roadmap](/concepts/roadmap#the-data-plane) for the roadmap item that closes each gap.

## The deployment profile

One document names all three profiles. `create-agent-workspace <dir> --cloud aws|gcp|azure|local`
writes `agent-workspace.yaml`, validates it before anything else exists, and renders the
deployment's `.env`, its Compose file, its Helm values overlay and its Terraform variables from
it — so a placement decision is stated once and never written twice.

```yaml title="agent-workspace.yaml (illustrative)" claim="illustrative"
apiVersion: agentworkspace.dev/v1
kind: Deployment
cloud: gcp
storage:
  relational: cloud-sql # a postgres:// URL, or that cloud's managed PostgreSQL by name
  objects: gcs://acme-ai-files # s3://, gcs:// on GCP, or local-filesystem where supported
  secrets: secret-manager # local-key, or secret-manager on GCP
runtime:
  default: cloud-run-service # local | docker | kubernetes | cloud-run-service | aca-sessions
identity:
  oidc: https://accounts.google.com
  bootstrapAdmin: ops@acme.example
```

A placement the platform has not implemented is **refused where it is written**, not accepted and
then ignored: `kms` outside AWS, `gcs://` and `secret-manager` outside GCP, and `azblob://` and
`key-vault` outside Azure, plus driver ids the runtime contract lists with no code behind them.
Every refusal names the offending field.

"Validated" means two things. Always, before any file is written: the document is schema-valid,
every URL scheme is one this release serves, and the cross-field rules hold. With `--validate`, and
only for a store whose credential is present: a connectivity probe — `select 1`, a bucket head, an
OIDC discovery fetch. Every probe is a read, so validation never changes the account it is pointed
at: a bucket that does not exist yet is reported as `missing`, not created, which is what makes a
typo in `storage.objects` visible instead of silently provisioned. `agent-workspace validate`
re-runs both against an existing project. The profile schema is published at
`https://unpkg.com/@indx-workspace/cli@latest/schema/agent-workspace.schema.json`, and
`agent-workspace validate` checks a profile against it.

unchanged, and an operator may still set them by hand (the generated `.env` is the same list; a value left blank there is a deployment that will not
start):

| `--cloud` | Also rendered                                                   | Default sandbox driver |
| --------- | --------------------------------------------------------------- | ---------------------- |
| `local`   | the Compose project                                             | `docker`               |

Each rendered artefact carries only what the operator must supply. The Helm overlay is the four
images the chart runs — one per Deployment, plus the sandbox image — because the chart defaults
everything else and each flavour file already sets its cloud's storage class and load-balancer
annotation; the Terraform artefact is the bootstrap administrator and the four digest-pinned
images, the variables those modules declare with no default. There is no `infra/terraform` module
for AWS, so `--cloud aws` renders none — an EKS cluster you already run is installed with the
chart.

A rendered `deploy/terraform/<module>.auto.tfvars.json` is applied by copying it into
`infra/terraform/<module>/` and running Terraform there — Terraform auto-loads
`*.auto.tfvars.json` only from the directory it runs in, and the generated `deploy/terraform/`
holds no `.tf` file of its own:

```sh title="illustrative" claim="illustrative"
cp acme-ai/deploy/terraform/gcp-cloudrun.auto.tfvars.json infra/terraform/gcp-cloudrun/
terraform -chdir=infra/terraform/gcp-cloudrun apply
```

`--cloud azure` renders no chart overlay, because the chart serves the S3 environment contract
only, while the Azure profile defaults to an `azblob://` container. The Container Apps module
supplies the native Blob endpoint and managed identity. Naming an `s3://` bucket in the profile
brings the existing chart path back.

## One storage URL

`AW_STORAGE_URL` names the store for files, skills and session transcripts in one URL; its four
forms are on [Configuration](/getting-started/configuration#tell-the-server-where-files-live). Each
object is stored as `workspaces/<workspace id>/<area>/<object id>` under the URL's prefix. The path
a person sees, such as `reports/q3.pdf`, is a row in the platform's PostgreSQL catalog, so renaming
or moving a file changes that row and never copies the bytes. A file is listed, searched or granted
to a run only once its row is `ready`: every save reserves a `pending` row, writes the bytes, then
confirms the row with the size and checksum it measured.

### Which stores sign links

A signed link lets a browser or `aw` upload or download a file straight from the store, so the
bytes never pass through the control plane. Each link works for one file, for 5 minutes by default
and 15 at most.

| Scheme      | Signs upload and download links                                                                                                     | Binds the upload's size into the link                                                                                        |
| ----------- | ----------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| `s3://`     | Yes                                                                                                                                 | Yes: the store refuses a body of any other length                                                                            |
| `gcs://`    | Yes, with the server's own Google identity                                                                                          | Yes                                                                                                                          |
| `azblob://` | Yes, with a user-delegation key from the managed identity                                                                           | No: a SAS cannot carry a length, so `upload-complete` deletes an object larger than declared or over the limit              |
| `file://`   | No: the link routes answer `501 direct_transfer_unsupported`, and `aw` and the SDK upload through the control plane instead         | No                                                                                                                           |

A browser's `PUT` to a signed link is cross-origin, so the bucket needs a CORS rule that allows
`PUT` and the returned headers from the web service's origin. The bundled SeaweedFS of a Compose
project allows only the origins in `SEAWEEDFS_ALLOWED_ORIGINS` in its `.env`; for a `.env` an
older CLI wrote without it, `agent-workspace doctor` prints the line to add. A workspace holds at
most 100 unfinished signed uploads (`429 too_many_pending_uploads`), and makes at most 60 link
requests a minute on one server (`429 link_rate_limited`, with `Retry-After`).

### Size limits

Each limit is defined once in the code, and a CI check fails if a copy of it appears anywhere else.

| What                                                    | Limit                                                                                                         | Defined as                            |
| ------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------- | ------------------------------------- |
| One upload through the control plane (`POST /api/files`) | 64 MiB                                                                                                        | `MAX_UPLOAD_BYTES`                    |
| One upload on a signed link                             | 5 GiB at most; `AW_STORAGE_SIGNED_UPLOAD_MAX_BYTES` lowers it for a deployment, checked at `upload-complete` | `SIGNED_UPLOAD_HARD_MAX_BYTES`        |
| The files delivered into one run, in total              | 128 MiB                                                                                                       | `RUN_FILES_MAX_BYTES`                 |
| One session-state snapshot                              | 32 MiB                                                                                                        | `SESSION_STATE_BLOB_MAX_BYTES`        |
| One skill upload request                                | 16 MiB                                                                                                        | `MAX_SKILL_REQUEST_BODY_BYTES`        |
| One chat or run attachment                              | 10 MiB                                                                                                        | `SURFACE_ATTACHMENT_MAX_BYTES`        |
| All attachments of one visitor session                  | 50 MiB, in at most 20 files                                                                                   | `SURFACE_ATTACHMENTS_MAX_TOTAL_BYTES` |

### Migrating from the old variables

The old storage location variables are ignored: the server reads none of them. Each one still set
logs one `storage_setting_ignored` warning that names it and never its value. With
`AW_STORAGE_URL` unset, nothing is read from the old location: files, skills and session state are
off until `AW_STORAGE_URL` is set. `agent-workspace doctor` then fails its storage check and
prints the `AW_STORAGE_URL=` line that points at the old location. Files, skills, chat attachments
and run delivery all go through one catalog service, so there is no second path that reads an
area's own folder or bucket if the service cannot start: those routes answer `503`. Each row maps
an old setting to the URL form:

| Old setting                                                                     | `AW_STORAGE_URL`                                                                    |
| ------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------- |
| `OBJECT_STORAGE_BUCKET=<bucket>` (S3, the old default)                          | `s3://<bucket>`                                                                     |
| `OBJECT_STORAGE_ENDPOINT=<endpoint>` (S3-compatible)                            | add `?endpoint=<endpoint>`                                                          |
| `OBJECT_STORAGE_PUBLIC_ENDPOINT=<origin>`                                       | add `publicEndpoint=<origin>`                                                       |
| `OBJECT_STORAGE_FORCE_PATH_STYLE=true`                                          | add `pathStyle=true`                                                                |
| `AWS_REGION=<region>`                                                           | add `region=<region>`. `AWS_REGION` is still read when the URL has no region        |
| a GCS bucket `<bucket>` with `GCP_PROJECT=<project>`                            | `gcs://<bucket>?project=<project>`                                                  |
| an Azure Blob container `<container>` on `https://<account>.blob.core.windows.net` | `azblob://<account>/<container>`                                                 |
| the same in a sovereign cloud, on `https://<account>.blob.core.usgovcloudapi.net`  | add `?endpoint=https://<account>.blob.core.usgovcloudapi.net`                     |
| the three local roots `<dir>/files`, `<dir>/skills` and `<dir>/sessions`        | `file://<dir>` (`<dir>` absolute, e.g. `file:///var/lib/agent-workspace`)           |
| `OBJECT_STORAGE_ACCESS_KEY_ID` and `OBJECT_STORAGE_SECRET_ACCESS_KEY`           | No change. They stay in the environment and never go into the URL                   |

The bundled SeaweedFS of a Compose project is
`s3://agent-workspace?endpoint=http://seaweedfs:8333&publicEndpoint=http://localhost:8333&pathStyle=true`
with `AW_STORAGE_CREATE_BUCKET=true`: the same bucket, so its objects stay where they are. Once the
URL is set, delete the old variables.

The Terraform modules already write `AW_STORAGE_URL`: Cloud Run as `gcs://<bucket>?project=<project>`
(the web service no longer gets `GCP_PROJECT`, which it never read), and Azure Container Apps as
`azblob://<account>/<container>`, with `storage_blob_endpoint` as its `endpoint=` in a sovereign
cloud. On Helm, set the chart's `storage.url`, or keep the URL in the object-store Secret: an empty
`storage.url`, the default, leaves the Secret's value in place ([Kubernetes](/guides/deploy#kubernetes)).

## Per cloud today

### AWS

RDS for PostgreSQL and S3 are both native and work today through `DATABASE_URL` and the
`AW_STORAGE_URL` above — no AWS-specific code path exists because none is needed.
There is no `infra/terraform` module for AWS and no `values-eks.yaml`-paired Terraform for the
database or object store; `infra/helm/agent-workspace/values-eks.yaml` sets only the storage
class (`gp3`) and the load-balancer annotation for an EKS cluster the operator has already
provisioned. Secrets: credentials stay envelope-encrypted in PostgreSQL as everywhere else;
`MASTER_KEY_PROVIDER=kms` decrypts the deployment master key from a KMS-wrapped blob
(`AWS_KMS_KEY_ID`, `AWS_KMS_ENCRYPTED_MASTER_KEY`) instead of reading `MASTER_ENCRYPTION_KEY`,
with the live proof still pending; there is no Secrets Manager integration. Sandbox driver: `aws-ecs` and
`aws-agentcore` are named in the runtime contract with no implementation in `packages/runtime`
(both are out of scope: no managed driver is selected).

### Google Cloud

Cloud SQL for PostgreSQL is native (`DATABASE_URL`). The Cloud Run module grants the web service
account `roles/storage.objectAdmin` on its object bucket; `AW_STORAGE_URL=gcs://<bucket>?project=<id>` selects the
native Google client through ADC, in the [one object layout](#one-storage-url), with no HMAC key.
The module also stores the unchanged 32-byte platform master key in a regional Secret Manager
secret protected by a dedicated Cloud KMS CMEK. `MASTER_KEY_PROVIDER=secret-manager` reads it before
the database opens. Rotate the wrapping key by letting Cloud KMS create a new primary version (the
module sets a 90-day rotation period), then add a new Secret Manager version with the same plaintext;
new versions use the primary KMS version while the application fingerprint and stored envelopes
remain valid. Do not disable or destroy a KMS version while any enabled secret version still needs
it; changing the 32-byte plaintext is a separate envelope-key migration, not this procedure.

Upgrading a Cloud Run deployment to the release that carries migrations `0024` and `0025` is a
single-revision cutover: the previous release cannot run against the migrated database, and `web`
migrates as it starts.
Back up Cloud SQL, then scale the `web`, `gateway` and runner-manager services to zero (or route no
traffic to their previous revisions and let the instances stop) before the new revisions are
deployed. Rollback means restoring the backup together with the previous images.

The release that carries migrations `0026` and `0027` (the engine-scoped session store) is a
single-revision cutover too, for a different reason: `0027` copies every Claude transcript into the
new store once, and a previous revision still serving during a rolling update would keep writing
turns to the old tables that nothing copies.
Take the same steps — back up Cloud SQL, scale the previous revisions to zero or route no traffic to
them and let the instances stop, then deploy — and roll back the same way.

Both adapters have deterministic fake suites, but this page deliberately keeps the two GCP cells
partial: the required real-bucket and decrypt-after-rotation proof has not been recorded. Sandbox
driver: `cloud-run-service` is implemented in
`packages/runtime` and has a Terraform module (`infra/terraform/gcp-cloudrun`), but
no managed driver is the selected default, so it has no live isolation proof; `gke-agent-sandbox` and `cloud-run-sandbox` are named only.

The opt-in proof suites never create a bucket, secret, or key. Point them at resources the operator
has already scoped, then run:

```sh title="illustrative" claim="illustrative"
TEST_GCS_BUCKET=<throwaway-bucket> TEST_GCP_PROJECT=<project> \
  pnpm exec vitest run --project @agent-workspace/core packages/core/src/storage/gcs-store.live.test.ts

TEST_GCP_MASTER_KEY_SECRET_BEFORE_ROTATION=projects/<project>/secrets/<secret>/versions/<old> \
TEST_GCP_MASTER_KEY_SECRET_AFTER_ROTATION=projects/<project>/secrets/<secret>/versions/<new> \
  pnpm exec vitest run --project @agent-workspace/core \
    packages/core/src/secrets/google-secret-manager-master-key.live.test.ts
```

The bucket suite deletes only its random `agent-workspace-live-*` prefix. The key suite reads two
numbered versions and proves an envelope sealed before the CMEK rotation still opens afterward; it
does not print either payload.

### Azure

Azure Database for PostgreSQL Flexible Server is native
(`infra/terraform/azure-container-apps/storage-database.tf`). Files and skills use Azure Blob
Storage through the native SDK and a private container. The web app's managed identity has the
container-scoped `Storage Blob Data Contributor` role; transcripts and runtime-verification state
remain on the Azure Files mount because they are not `ObjectStore` consumers. The same identity
loads the platform master key directly from Key Vault, so the key is absent from rendered profiles,
Terraform inputs and Container App environment variables. Sandbox driver: `aca-sessions` is implemented in
`packages/runtime` with a full Terraform module (`infra/terraform/azure-container-apps/sessions.tf`)
providing one Hyper-V-isolated session per run, documented as a **preview**, not a production
baseline; it stands the same way as Cloud Run — implemented, not
yet live-verified.

## How a file, a skill and a secret move through it

```mermaid
sequenceDiagram
  participant Dev as Developer (SDK)
  participant API as Control plane
  participant Obj as Object store
  participant DB as PostgreSQL
  participant Run as Runner
  participant SB as Sandbox
  participant GW as Gateway
  Dev->>API: files.upload(path, bytes)
  API->>DB: reserve a pending catalog row (path, new object id)
  API->>Obj: stream to workspaces/<workspace>/files/<object id>, measuring size and SHA-256
  API->>DB: confirm the row as ready
  Dev->>API: skills.import({ name, files })
  API->>Obj: the same four steps, under the skills area
  Dev->>API: runs.start(agentId, { prompt })
  API->>Run: launch; the request lists each granted file by path, mode, size and checksum
  API->>Run: stream the granted files and skills as one archive
  Run->>SB: unpack it and check every checksum (a read-only grant as 0o555 dirs / 0o444 files)
  Run->>GW: request a per-run token
  SB->>GW: model call with the per-run token
  GW->>GW: resolve the stored provider credential (never sent to SB)
  Note over Run,Obj: after the run, outputs/ and the profile's persistPaths are saved under runs/<runId>/outputs/
```

A run request carries references to the granted files, never their bytes. The control plane
streams the files into the runtime as one archive, so its memory stays flat up to the 128 MiB a run
can carry, and the runtime refuses to start the engine when a file's checksum does not match
(`422 run_file_checksum_mismatch`). After a run completes, the agent's own `outputs/` directory
comes back to the workspace under `runs/<runId>/outputs/` when the agent may write files; a runtime
profile's `persistPaths` come back after any outcome. A `read-write` grant of a
[storage connection](/guides/storage-connections) writes the run's new and changed files back to
that bucket instead, and never deletes one (`apps/web/server/runs/launcher.ts`,
`apps/web/server/compose/storage-writeback.ts`).

Credentials are resolved only inside the gateway: a sandbox holds a short-lived, run-scoped token,
never the stored provider key, and the gateway substitutes the real credential only when
forwarding the request onward ([Choose models and runtimes](/building/models-and-runtimes)).

## What never changes

- **PostgreSQL is the only relational store.** Every durable row — workspaces, principals,
  agents, runs, events — lives there; no cloud's own managed-service equivalent changes the
  application's schema or query layer, only which server answers `DATABASE_URL`.
- **Credentials are write-only.** A value goes in once, is never returned by any response
  schema, and reaches a sandbox only as a short-lived, run-scoped substitute the gateway mints —
  never the stored key itself.
- **A sandbox reaches the gateway and nothing else, unless the profile widens it.** A runtime
  profile's network policy (`none`, `restricted`, `open`) is a required, explicit choice on the
  profile, not something a driver grants by default — and a driver that cannot enforce a policy
  refuses it rather than pretending ([Self-host Agent Workspace](/building/self-hosting)).
