## Find your use case

If you have a use case of your own, find the closest row and read its tutorial: its "Where the
SDK stands" section is the honest answer to "can I build this today, and what will I have to
write myself?"

| If you need an agent that… | Tutorial | What it teaches | Difficulty |
| --- | --- | --- | --- |
| runs on the engine, model, frontend and servers you already chose | [0. Your stack](/tutorials/your-stack) | the generator's flags, engines, models, `openapiTool`, `postgresTool`, MCP, skills, widget and React, deploy | Starter |
| answers from manuals or rule books, with citations | [1. Manual search](/tutorials/manual-search) | a skill, an MCP search server, a file grant, a side-panel surface, evals, a backend citation check | Starter |
| reuses past drawings to draft a new one | [2. CAD drawing](/tutorials/cad-drafting) | a skill script with `runCommands` and `writeFiles`, read-write files, a person's choice between two runs, a stored policy | Advanced |
| prices work from an ERP and a cost model | [3. Quotation](/tutorials/quotation) | `openapiTool` with a `secret` and one approved write, a skill script, a policy ceiling | Intermediate |
| checks approval requests against the rules | [4. Ringi review](/tutorials/ringi-review) | read-only MCP tools, an approved `openapiTool` comment, a fixed output format as a skill, a backend that starts one typed run per revision, a side panel | Advanced |
| answers customers on your website | [5. Customer inquiry](/tutorials/customer-inquiry) | an MCP server with signed-token scope and masking, a dock widget, sessions, handoff to an operator, ratings into evals | Advanced |
| consolidates scattered spreadsheets | [6. Excel consolidation](/tutorials/excel-consolidation) | MCP file search, two skill scripts, a person's approval of the plan, a number guard | Advanced |
| reviews documents against a checklist | [7. Contract review](/tutorials/contract-review) | file grants, two skill scripts that read Word, no MCP server, judged evals, a must-flag check | Intermediate |
| turns meetings into tasks in a tracker | [8. Meeting minutes](/tutorials/meeting-minutes) | a skill script, an `openapiTool` write that runs only for an approved call, a person's approval between two runs | Advanced |
| guides someone step by step and logs the result | [9. Maintenance troubleshooting](/tutorials/maintenance-troubleshooting) | `search_files` narrowed per technician and an approved `openapiTool` write, one run per reply, a check on every turn, escalation, ratings into evals | Advanced |
| analyses incidents from past cases, kept confidential | [10. Quality defects](/tutorials/quality-defect) | an approval-gated `openapiTool` over the QMS with caller identity, a skill with a checker script, an offline policy ceiling, a revision after review | Intermediate |

**Starter:** read-only, no human step. **Intermediate:** a script or a backend check you own.
**Advanced:** a person's step between runs, a write to another system, or webhook and session code
in your backend.

## What a tutorial is here

The six chapters of the path teach one feature per page on one running example, a support
agent. A tutorial does the opposite: it takes one real business task and puts every feature it
needs together in one project, the agent definition, its skills, its MCP servers or tools, its
file grants and policy, a surface, an eval file and the backend code around the run. Every
tutorial page has the same shape:

- **At the top:** what you will build, what you will learn, and how long it takes to read and to
  do.
- **The result:** a screenshot of the finished agent answering a real question.
- **How it works:** one diagram from the request to the person who decides, and the files you
  will write.
- **Before you start:** what you need, and where the code comes from.
- **Build it:** numbered parts, one per file, each ending with a **Check** you can verify.
- **Run it:** offline in the test suite with no API key, then on your own workspace.
- **Where the SDK stands:** the benchmark verdict for that use case, and what is still your code.

### How the tutorials use the path

| Chapter | What the tutorials take from it |
| --- | --- |
| [1. Run your first agent](/path/first-agent) | The prerequisite for all of them: a project under `aw dev` and a model key. |
| [2. Build your agent](/path/build) | Every tutorial: `defineAgent`, skills, MCP servers or `openapiTool`, file grants, permissions and the project's policy ceiling. |
| [3. Test and improve it](/path/test) | Every tutorial has an eval file run with `aw eval`, and most set a promotion bar; 5 and 9 turn rated runs into eval cases. |
| [4. Put it in your product](/path/embed) | Every tutorial defines a surface and calls the agent from a backend with `runs.start` and `runs.follow`. |
| [5. Ship it to your servers](/path/ship) | Not covered by the gallery, which runs on `aw dev` or your workspace; [Tutorial 0](/tutorials/your-stack) shows `aw deploy` in its last part. |
| [6. Run it for your team](/path/operate) | Not covered. Per-person scope, which most verdicts mark as missing, is not on the roadmap yet: no connector learns who is asking today. |

For the six recurring shapes an agent takes (an in-product copilot, a team workspace, backend
automation and so on), see [Use cases](/concepts/use-cases).

## How the tutorials are tested

Each tutorial is also a **benchmark**: the table below says, capability by capability, where the
SDK stands today, and every verdict in it is backed by an offline test.

Every cell is scored by one rule:

- ✅ the platform does it: the use case writes no code of its own for this capability.
- 🟡 the use case does it with code it ships (an MCP server, a skill script, a backend step, a
  second run) and its offline suite exercises that code; or the platform does most of it and the
  use case covers the missing part itself.
- ❌ the use case does not do it: the step is left to a person, to a system the gallery does not
  build, or is impossible today.
- — not needed.

Score: ✅ = 1, 🟡 = 0.5, ❌ = 0, averaged over the capabilities the use case needs.

<Note>
  An agent can use a tool written with `defineTool()`: `aw dev` runs it on your machine, and a
  version that uses one can be promoted on a deployment whose operator turned the tool sandbox on
  (see [Tools from code](/guides/tools-from-code)). The sandbox is off by default, so every search
  or write tool in this gallery is still an MCP server you run, and that is how the verdicts below
  are scored.
</Note>

### How each verdict is proved

Every use case has an offline test suite that runs with no API key. A verdict
cites one of four kinds of evidence:

| Evidence | What runs | What it proves |
| --- | --- | --- |
| `contract` | The use case's own tests. The project's agents, surfaces, skills and evals are loaded through the same contract `aw check` applies; the use case's MCP servers and skill scripts run for real; its backend runs against a scripted workspace whose tool results are the real servers'. | The definition is valid, the tools work, and the backend code handles a run correctly. Not that a model makes good decisions: that is what `aw eval` on a workspace is for. |
| `probe` | A gap probe in `harness/probes.ts` asks the published contracts whether a capability exists. | The capability is missing today. The probe fails the day it arrives, so this table cannot go stale. |
| `source` | Nothing; the cell cites a file in the platform. | What the code says, for facts no offline test can reach. |
| `live` | `aw eval` on a real workspace and model. | Run by you, not by CI. |
