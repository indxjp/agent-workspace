<Info>

- **Read this when:** you want to know what a line of the ready screen means, move a port, start in a directory you already have, or run `aw dev` without a terminal.
- **You will learn:** what `aw dev` starts, which ports and settings it uses, and how it decides the model and the runtime profile.
- **Used in:** [Quickstart](/getting-started/quickstart), [Troubleshooting](/getting-started/troubleshooting).

</Info>

`npm run dev` in a new project runs `aw dev`. It starts the published local runtime
(`@indx-workspace/embedded`) from the project's own dependencies: one Node process with an embedded
PostgreSQL. It signs `aw` in, creates the `default` model connection from your key, pushes the
project's agents, surfaces and skills, and then syncs again on every save. In 0.6.9,
`npx aw dev --help` lists `aw dev [--quiet] [--verbose] [--open | --no-open] [--sandbox <local|docker>]`.
The next release adds `--port <n>`, and the subcommands `aw dev status` and `aw dev stop`
([below](#start-it-in-the-background)).

## The ready screen, line by line

`aw dev` reads `ANTHROPIC_API_KEY` (and `ANTHROPIC_BASE_URL`, if set) from its environment. Set it
in the shell, never in a file; no key is written to the project. The runtime's own output (initdb,
PostgreSQL, Next) goes to `.aw/logs/runtime.log`, which the generated `.gitignore` lists. It prints
one screen when everything is up. This is the real output of 0.6.9 on a first start, with the
password masked:

```text title="Output"
> dev
> aw dev

Sign in at http://127.0.0.1:3000 as admin@localhost.test with password … (shown once; it is kept in /home/node/my-agent/.agent-workspace/local-secrets.json)
model connection: default (anthropic)

  Agent Workspace · my-agent · local

  try       http://127.0.0.1:3000/p/s/main/try
  console   http://127.0.0.1:3000  sign in as admin@localhost.test · password in .agent-workspace/local-secrets.json
  chat      npx aw chat

    runtime   ready in 3.6 s   logs: .aw/logs/runtime.log
    model     default · workspace default model · key checked
    signed in as admin@localhost.test (workspace default)
    agent     assistant  (agents/assistant.ts)
    surface   main

  evals     3 cases · npx aw eval
  embed     <script src="http://127.0.0.1:3000/p/s/main/widget.js" async></script>
  react     https://docs.agentworkspace.indx.jp/building/react

  watching agents/ surfaces/ tools/ skills/ · edit a file and save
synced: skill refund-policy (new, 1 file) · "assistant" created at version 1
```

| Line | What it means |
| --- | --- |
| `Sign in at … with password …` | Printed by the runtime on the first start only, when it generates the console password. The password is kept in `.agent-workspace/local-secrets.json` (key `BOOTSTRAP_ADMIN_PASSWORD`). |
| `model connection: default (anthropic)` | The model connection `aw dev` created from your key. |
| `Agent Workspace · my-agent · local` | The project and the environment (`local`) it runs. |
| `try` | The surface's chat page. Open it to talk to the agent. |
| `console` | The web console: its URL, the owner email `admin@localhost.test`, and where the password is. See the [console tour](/getting-started/console-tour). |
| `chat` | The terminal chat: [aw chat](/cli/chat). |
| `runtime` | How long the start took, and the runtime log. |
| `model` | The connection, and `key checked` once the provider accepted the key (`stored key checked` when it runs on a key you pasted earlier). |
| `signed in as` | The identity `aw` uses inside this project, and the workspace (`default`). |
| `agent`, `surface` | One row for each agent and surface the project defines. |
| `evals` | The evaluation cases found under `evals/`, and the command that runs them. |
| `embed` | The one-tag chat widget for a web page. A page on another origin also needs `allowedOrigins` ([the widget does not load](/getting-started/troubleshooting#the-widget-does-not-load-on-my-page)). |
| `react` | Where the React component is documented. |
| `watching …` | The folders `aw dev` syncs. Each save prints one `synced:` line. |

On a terminal each status row starts with a tick, and a moved port adds a row such as
`✓ web       on :3001 (3000 was busy)`. With `NO_COLOR` set, or when the output is not a terminal,
the screen has the same content without colour or ticks. When the runtime stops on its own,
`aw dev` prints the last 20 lines of the log and its path.

<Note>

In the next release the password is never printed: the `console` row splits into three lines
(the URL, `sign in as …`, `password in …`), and the file moves to
`.agent-workspace/secrets/local-secrets.json`; an existing project's file is moved there for you.

</Note>

After the screen, on a terminal, `aw dev` asks `Open the chat in your browser? (Y/n)`; Enter opens
it. `--open` opens it without asking (also where there is no terminal) and `--no-open` never asks;
with `--quiet`, or when the output is not a terminal, it never asks (`--open` still opens). On WSL
the browser is the Windows one (`wslview`, else `cmd.exe start`).

Every save under `agents/`, `surfaces/`, `tools/` or `skills/`, or to `agent-workspace.yaml`,
syncs again and prints one `synced:` line, such as `synced: "assistant" version 2 (2 changes)`. The
line names the agent, also when you changed its surface.

## Flags

| Flag | Effect |
| --- | --- |
| `--quiet` | No ready screen. |
| `--verbose` | Stream the runtime's own output instead of only writing it to the log. |
| `--open` / `--no-open` | Open the chat page without asking, or never ask. |
| `--sandbox local` | Run agents on the in-process `local` driver (the default profile). |
| `--sandbox docker` | Run every agent in a Docker container; see [the Docker sandbox](/getting-started/troubleshooting#the-docker-sandbox-refuses-to-start-or-the-run-fails). |
| `--port <n>` | Next release: the web port. In 0.6.9, set `environments.local.port` instead. |

## Ports

The runtime uses four ports. When the project does not set `environments.local.port` and 3000,
4000, 8080 or 25432 is taken, `aw dev` moves all four to the next free set and says so
(`web on :3001 (3000 was busy)`). A port you set is never moved: it is reported as busy and nothing
starts.

| Role                | Default | Setting that moves it                                                 |
| ------------------- | ------- | --------------------------------------------------------------------- |
| web                 | 3000    | `environments.local.port` (next release also `aw dev --port` and `PORT`) |
| gateway             | 4000    | the web port, or `GATEWAY_PORT` in the project's `.env`               |
| runner              | 8080    | the web port, or `RUNNER_PORT` in the project's `.env`                |
| embedded PostgreSQL | 25432   | the web port, `AW_DATABASE_PORT` in `.env`, or `DATABASE_URL` instead |

The gateway, runner and database ports move with the web port: each is its default plus the web
port's distance from 3000, so `port: 3070` gives 4070, 8150 and 25502. A derived port above 49151
(the start of the operating systems' dynamic ranges) is not used: that service keeps its default
port. From web port 26720 up the database stays on 25432, from 44072 the runner stays on 8080, and
from 48152 the gateway stays on 4000. A `GATEWAY_PORT`, `RUNNER_PORT` or `AW_DATABASE_PORT` in
`aw dev`'s own environment turns the automatic move off; one in `.env` is still checked by the
runtime and refused when busy.

With a port set, `aw dev` checks all of them before it starts anything, reports every port that is
not free in one message, and starts nothing:

```text title="Example output (illustrative)" claim="illustrative"
error: the local runtime cannot start; nothing was started. These ports are not free:
  port 3000 (web) is already in use: stop the process that holds it, or set environments.local.port in agent-workspace.yaml to a free port below 49152
```

Change the port (`port: 3200` also moves the gateway, runner and database to 4200, 8280 and 25632)
or set the variable named in the message in a `.env` next to the project file.

## Which model and profile the first run uses

A message sent from the `try` page runs the agent on the workspace's default runtime profile,
`local`, which the runtime creates at start, with the `default` model connection `aw dev` set up
from `ANTHROPIC_API_KEY`. The runtime serves the surface's page, its try page and the one-tag
widget snippet from the same origin. The generated agent says `model: 'default'`, which names
that connection but no model id, so the run uses the deployment default model the local runtime
sets: `claude-sonnet-4-5` for Anthropic, or its newest dated release
(`claude-sonnet-4-5-YYYYMMDD`) when the provider's model list has only those. The console's chat
box says so: `Runs as assistant on claude-sonnet-4-5 or its newest dated release (default, the
deployment default).` See [Choosing a model at each level](/building/models-and-runtimes#choosing-a-model-at-each-level).

The `local` profile names the `local` driver, the runtime's in-process runner, which has no
isolation: commands run as you, so it is for development only. The web console says
`Runtime driver in force: local — No tenant isolation: commands run as the host user` on every
screen.

Inside the project, `aw` takes the URL from `agent-workspace.yaml` and the local key `aw dev`
stored, so no `AGENT_WORKSPACE_*` variable is needed — and none may be set to point it elsewhere:
`AGENT_WORKSPACE_URL` outranks the project file. `npx aw me` shows who `aw` is there:

```text title="Output"
principalId  94d853f8-6300-4d20-a0e5-d42173ee634e
kind         api-key
role         admin
workspaceId  1e878b84-ddbe-40fd-a876-1adb7caaa6c2
userId
label        aw dev local runtime 9i3RRbPJ
```

## What npm create asks and writes

`npm create @indx-workspace@latest my-agent -- --yes` takes the recommended answer to every
question, installs the dependencies, and never starts the server. Without `--yes`, on a terminal,
`npm create @indx-workspace@latest` asks eleven questions, each a menu (up and down move, space
toggles a multi-select, Enter accepts) or a typed value with the default shown:

1. `Project name (my-agent)`
2. `Which theme should setup start from?` (`support`, `copilot`, `knowledge`, `automation`, `review`, `blank`)
3. `Where should agents run their tools?` (`auto`, `local`)
4. `Who serves the agent's model?` (`anthropic`, `anthropic-compatible`, `openai`, `azure-openai`, `openai-compatible`)
5. `What is your first agent called?` (`assistant`)
6. `Which agent engine should it use?` (`claude-agent-sdk`, `openai-agents`, `pi`, `mastra`)
7. `Which internal tools should the agent call?` (`openapi`, `postgres`, `none`)
8. `Which permissions should the agent have?` (`readFiles`, `writeFiles`, `runCommands`, `unrestrictedNetwork`)
9. `What title should the chat widget show?` (`Assistant`)
10. `What is your brand colour?` (`#2f5fd0`)
11. `Which agent platforms should this agent also be published to?` (six platforms, or `none`)

It then lists the files and asks `Write these 10 files into …?`, then `Install dependencies now?`
and `Start it now?` (Yes is the default for all three); starting runs `npm run dev` and lands you
on the ready screen. `auto` for question 3 lets the runtime pick Docker when it is reachable;
`local` writes `runtime.default: local`. Without a person (a coding agent, or any run where `CI`
is set or stdin or stdout is not a terminal) nothing prompts; flags and `--answers <file>` set any
answer. See [Running without a person](/cli/overview#running-without-a-person).

`--install` / `--no-install` and `--start` / `--no-start` answer the last two questions (`--start`
implies `--install`); starting keeps `aw dev` in the foreground until Ctrl+C. `--yes` means
install, and do not start. Whatever was not done is printed as the next steps, in order, for your
shell. On Windows, with the key not set, the `--yes` run ends with:

```text title="Output"
Next steps:
  cd my-agent
  PowerShell: $env:ANTHROPIC_API_KEY="<your key>"
  cmd:        set ANTHROPIC_API_KEY=<your key>
  npm run dev
```

The project pins `@indx-workspace/aw`, `@indx-workspace/embedded` and `@indx-workspace/sdk`, pins
`@indx-workspace/cli` as a dev dependency (`aw deploy` imports its deploy steps from it), answers
npm's install-script prompt in an `allowScripts` block (pnpm's in `pnpm-workspace.yaml`), and its
`dev` script is `aw dev`.

## Start in an existing directory (aw init)

Run `npx @indx-workspace/aw init` there. On a terminal it asks the same setup questions as
`npm create`, theme first, lists the files and asks before writing. `--yes` takes the recommended
answers without asking, and without a terminal `--yes` is required. It writes the same files
`npm create` writes for the same answers (`agent-workspace.yaml`, the agent, the surface and
`AGENTS.md`), refuses to overwrite any file that exists and never edits `package.json`. It also
makes sure `.gitignore` lists `node_modules/`, `.agent-workspace/`, `.aw/` and `.env`: it creates
the file, or appends only the missing lines to yours. It then prints what to run next: `npm init -y`
when the directory has no `package.json`, the `npm install -D` line for the three packages at
`aw`'s version, the variables `aw dev` reads, and `next: npx aw dev`.

`aw init` takes the same setup flags as `npm create` (`--theme`, `--provider`, `--agent`, and the
rest; `npx @indx-workspace/aw init --help` lists them with their defaults), and a flag answers its
question so it is not asked.

## Stop it

Press Ctrl+C in the terminal that runs it. The runtime and its database can take a few seconds to
stop; without a terminal, 0.6.9 prints `interrupted`. The next release says
`stopping the local runtime…` at once. `npm run dev` starts it again with everything you made: the
data stays under `.agent-workspace/`, which `.gitignore` lists.

## Upgrade the local database

The embedded database is PostgreSQL 18. A project an earlier release ran has a PostgreSQL 17 data
directory (`.agent-workspace/postgres`, or `AW_DATA_DIR`), which PostgreSQL 18 cannot open.
`aw dev` then stops before anything else starts, changes nothing in the directory, and says the
data directory was created by another PostgreSQL major version.

To start with an empty database, move the directory aside and run `aw dev` again:

```sh title="illustrative" claim="illustrative"
mv .agent-workspace/postgres .agent-workspace/postgres-17
```

To keep the data, export it while the release that created it still runs, before you upgrade
`@indx-workspace/aw` and `@indx-workspace/embedded`. Any `pg_dump` of version 17 or later can read
it; this one comes from the PostgreSQL image, so nothing is installed on the host:

```sh title="illustrative" claim="illustrative"
docker run --rm --network host postgres:18-alpine \
  pg_dump -Fc "postgresql://agent_workspace:agent_workspace_local@127.0.0.1:25432/postgres" > local.dump
```

Then stop `aw dev`, upgrade the packages, move the directory aside as above, and start `aw dev`
once so it creates the new database. With it running, load the export over what it created:

```sh title="illustrative" claim="illustrative"
docker run --rm --network host -i postgres:18-alpine \
  pg_restore --clean --if-exists --no-owner \
  -d "postgresql://agent_workspace:agent_workspace_local@127.0.0.1:25432/postgres" < local.dump
```

Restart `aw dev` afterwards. Use the database port the ready screen names if it is not 25432.

## Start it in the background

`npm run dev` never exits, so a script or a coding agent starts it in the background and waits for
the ready screen. The generated `AGENTS.md` gives the command for each shell:

```sh title="From the generated AGENTS.md, bash and zsh (illustrative)" claim="illustrative"
mkdir -p .aw && nohup npm run dev > .aw/dev.out 2>&1 &
```

Then wait for the `try` row in `.aw/dev.out`, and check with `npx aw chat -p "hi"`.

<Warning>

`npx aw dev status` and `npx aw dev stop` arrive in the next release. In 0.6.9 there is no such
subcommand: `npx aw dev status` starts a second runtime, which fails on the first one's database
([details](/getting-started/troubleshooting#aw-dev-status-starts-a-second-runtime)). From the next
release, `npx aw dev status` exits 0 and prints the URL once the runtime is ready (`--json` prints
`{"running":true,"url":…,"port":…,"pid":…}`), and fails while it is still starting or stopped;
`npx aw dev stop` stops it, its runtime and its database.

</Warning>
