<Info>

- **Read this when:** you want to create or change an agent by describing it, in the console or on
  the command line, instead of filling in the form.
- **You will learn:** what the Builder does, what it always asks you first, how to read the approval
  card, where to go after a save, and how an admin lets an agent build agents.
- **You need:** a workspace where an admin has enabled the `builder` feature, and a role that can
  create agents.

</Info>

The Builder is a built-in agent that drafts other agents. You describe what you want; it looks at
what your workspace has, writes a draft, checks it, and asks you before it saves anything. It
never promotes an agent: that stays your decision.

The feature is off until an admin enables it. Until then the console shows no Chat option on the
new-agent page, and the Builder's tools answer `builder_disabled`.

## Start a chat

Open **New agent** and switch from **Form** to **Chat** (`/agents/new?mode=chat`). The chat is on the
left. On the right is a live preview of the definition the Builder is drafting, with each change
labelled. Type what you want, for example "an agent that helps with expense refunds".

If the draft names something your workspace lacks, such as a connector, the Builder says so and asks
you instead of guessing. Answer in the chat, or use "Ask the Builder to change this" on the preview.

## Approve each step

Every save, trial and evaluation (running the eval cases) stops and asks you first. Nothing is
saved, run or scored until you approve it, and an approval admits that one call only. Validating a
draft (`draft_check`) runs without asking, because it changes nothing.

| Step  | What it does                                 | Cost cap            |
| ----- | -------------------------------------------- | ------------------- |
| Save  | Writes the draft as a new version on `local` | None                |
| Trial | Runs the draft once on a sample input        | $0.30               |
| Evaluation | Scores the draft on eval cases          | $0.30 for each case |

A trial runs the agent for real, so it can change real systems through the connectors the agent
holds. Read the card before you approve it.

## Read the diff

The approval card shows the exact change, taken from what the Builder is about to send, not from
what it says in the chat. For a save it is the difference against the base version; for a trial it
is the input and the budget cap; for an evaluation it is the case names and the cap.

When a change lowers a guard, the card adds a warning you can read before approving:

- the agent can skip permission checks;
- the agent gets the whole Claude Code tool set, or one more tool in an explicit set;
- a hard deny on a tool is removed;
- the agent can use a tool without asking.

Reject the card and nothing is written.

## After a save

The preview says "Saved as version N on local" and offers three links:

- **Try it** opens a new chat pinned to that version.
- **View history** opens the agent's versions, where the version shows the source "Builder".
- **Promote** opens the Release section, where you promote the version through the eval gate.

The Builder itself never promotes. Production moves only when you do it.

## Build from the command line

`aw agents new --from-prompt "<text>" [--out <dir>]` runs the same chat on your terminal. Every
save, trial and evaluation shows what it will do and waits for `y`. There is no `--yes`, and it needs a
terminal on stdin and stdout. A saved agent is written as `agents/<name>.ts` and `.md`.

## Let an agent build agents

An admin can let a named agent use the Builder's tools, so that it creates narrower specialist
agents for people. The same `builder` feature switch applies, and no agent has this until the
deployment names it.

**Allow an agent.** List its exact name under `builder.allow` in the deployment's
`AW_DEPLOYMENT_POLICY`:

```json title="illustrative" claim="illustrative"
{ "builder": { "allow": ["hr-onboarding-coordinator"] } }
```

- Only the deployment's policy grants this. A project's `policy:` never does.
- A missing `builder` key, an empty list, or a name that is not an exact match allows no agent.
- Only an Owner or Admin can create an agent with a listed name, or rename one onto it. Anyone else
  gets `403 builder_name_reserved`.
- An agent that was made by an agent never gets the tools, even if its name is listed. Its calls
  are refused `not_allowed_to_build`.

**Ask a person before each write.** The gateway refuses `draft_save`, `trial_run` and `evals_run`
(`approval_required`) until a person approves that exact call. To show the person the approval card,
list `mcp__aw-control__draft_save`, `mcp__aw-control__trial_run` and `mcp__aw-control__evals_run` in
the creating agent's `requireApproval`; that setting belongs to the Claude engine.

**What the server checks.** The model cannot talk its way past these, whatever a document it read
says:

- **Never wider than the creator.** A draft may not give the new agent more than its creator has:
  more permissions, file access, connectors, skills or subagents, or looser limits. Settings the
  check cannot compare must equal the creator's. The refusal is `creator_cannot_widen`, `details`
  lists each path (such as `definition.agent.permissions.runCommands`), and nothing is saved. A
  trial or an evaluation may only target an agent that is no wider than the creating agent.
- **Daily quota.** Each workspace may create 20 agents per UTC day, whoever creates them, people
  included. The 21st is refused `quota_exceeded`.

**See who made an agent.** An agent made by an agent carries `createdByAgent` (the creating agent,
its version and the run) in the API, the SDK and `aw agents get`. A person-made agent has none. The
`agent-created` audit row names the creating agent.

**Cap the spend.** `maxCostPerDayUsd` in the same policy caps model spend per UTC day for the whole
workspace, not only for these agents. A run start over the cap is refused `429
daily_cost_cap_reached`, and a run in progress ends at its next model call.

**Unused agents are archived.** An agent made by an agent, 30 days old and with no run in the last
30 days, is archived automatically. A person-made agent never is. An archived agent refuses every
run start with `409 agent_archived`, and is left out of the agent list unless you ask for it
(`GET /api/agents?archived=include`, or `agents.list({ archived: 'include' })` in the SDK).

**Restore an archived agent.** Call `POST /api/agents/:id/restore` (no body), `agents.restore(id)` in
the SDK, or run `aw agents restore <id>`. The Owner, an Admin or the agent's owner may restore it.
The agent is skipped by the archive sweep for 30 days after a restore. In the console, an archived
agent's page shows an Archived badge and, to anyone allowed to restore it, a Restore button; the
agent list hides archived agents unless you tick Show archived.
