## agentFromVersionBody

The inverse of `toAgentVersionBody` for an Agent Workspace project: the agent a body came
from, with what the body only names taken from the project. Nothing is left out silently.

- Every `resources.files` grant becomes `files(path, access)`, in body order, including those
  knowledge implied, so `toAgentVersionBody()` appends nothing and gives the same list.
- Each `resources.connectors` name becomes the tool a module exports under that name (the
  exact value, so spec, `allow`, auth and `identity` survive; `imports` says which module), or
  `mcp(name)` when `project.connectors` has the name (its entry is returned in `connectors`).
- `aw-dev-tools` becomes the code tools `source.codeToolNames` names (else `body.toolBundles`,
  in the bundles' name order), each the `defineTool()` export of that name, expanded in place.
  A bundle that pins another declaration than the module's tool, or that `codeToolNames` does
  not name, is dropped at `toolBundles.N` with its tool; so is a named tool with no bundle.
  `digest` is not compared: the SDK has no bundle bytes, and push pins it again. A bundle with
  no declaration (written before hosted sandboxes) matches by name.
  A repeated name, a name that a connector or module tool also has, and `codeToolNames` for a
  body with no `aw-dev-tools` are drops too (`codeToolNames.N`, the connector entry, `codeToolNames`).
- A name no module and no connector supplies (an inline tool looks the same), a name both
  supply (push refuses a tool with a connector's name), and code tools no source names or no
  module exports are drops.
- Last, the agent goes through `toAgentVersionBody()` again and the result is compared with
  the body, `toolBundles` aside: every differing path no drop covers becomes a drop, so a body
  field `defineAgent()` cannot write is reported at its path.

```ts
agentFromVersionBody(source: AgentVersionSource): { readonly value: AgentFromVersionBody; readonly dropped: readonly VersionBodyDrop[]; }
```

## defineAgent

Defines one agent as code. The input is checked now — names, model, engine settings, limits,
that every tool was made by `mcp()`, `openapiTool()`, `postgresTool()` or `defineTool()` and every skill and
file by `skill()` or `files()`, and that each appears once (tools by connector name, across
kinds) — and the result is the input as written, frozen and branded, ready for
`toAgentVersionBody`.

`subagents` are kept as names (a `defineAgent()` value gives its `name`), none repeated and none
the agent itself; a `connector` knowledge source must be one of the agent's `mcp()` tools.

```ts
defineAgent(input: DefineAgentInput): DefinedAgent
```

## toAgentVersionBody

Turns a defined agent, and its surfaces, into the body of an agent version — what `aw push`
saves and `aw check` dry-runs. The result is the parsed `AgentVersionBodySchema` output, so its
key order is fixed and two calls on the same definition are deep-equal.

How the definition maps:

- `model` left out or `'default'` → `modelConnectionName: 'default'`, `model: null`; the server
  resolves `default` to the workspace's connection of that name, else the deployment default
  (contract C7). Another string → that connection, `model: null`; `{ connection, id }` → that
  connection and model. `runtimeProfileName` is always `null`: null for the workspace's
  default runtime profile (none: runs are refused until the agent names one).
- `permissions` → all four switches, any left out `false`.
- `tools`, `skills` and `files` → `resources.connectors`, `resources.skills` and
  `resources.files`, in the order written; the skill allowlist names every assigned skill. Every
  tool lands in `resources.connectors` by its connector name: an `mcp()` tool's connector, an
  `openapiTool()` or `postgresTool()` tool's `name` (contract C15). `toolDefinitionsOf`
  gives what registers the catalog connectors.
- `description`, `subagents` (as `{ name }`, in the order written) and `knowledge` → the same
  keys, each absent when the agent leaves it out. Every `files` knowledge path the agent does
  not already grant is appended to `resources.files` with `read` access; a path it grants keeps
  its access. A `connector` source is already in `resources.connectors` through its `mcp()` tool.
- `engine.requireApproval` is stored as the policy's `requireApproval`, sorted and without
  duplicates; an empty list changes nothing.
- `engine.handoff: true` is stored as the policy's `handoff: true` and forces the stored policy;
  left out changes nothing.
- `engine` left out → `options.defaultEngine` (the project's `engine`, contract C12), else
  `claude-agent-sdk`.
- The policy is **compiled** (`policySource: 'compiled'`) when the engine is `claude-agent-sdk`
  and no limit has a value (`limits` left out, `{}` or every limit `undefined`) and no
  `autoApprove` or `requireApproval` rule is declared: it is then exactly the policy the server
  compiles from the permissions and skills, and follows later changes to them. It is **stored**
  otherwise — any limit with a value, any `autoApprove` rule (the policy's `tools.autoApprove`,
  nothing else changed), any `requireApproval` rule, `handoff: true`, or any other engine, even with no settings, since the server compiles a policy only
  for its default engine.

```ts
toAgentVersionBody(agent: DefinedAgent, options?: ToAgentVersionBodyOptions): AgentVersionBody
```
