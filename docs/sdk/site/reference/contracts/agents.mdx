## AgentDefinitionSchema

K-1: one agent as a portable file (`agent.json`) — what `aw.agents.export(id)` produces and
`aw.agents.import(definition)` recreates in any workspace.

- **Name-keyed.** Skills, connectors, the model connection, the runtime profile and files are
  referenced by name (files by workspace path), and resolved inside the destination at import.
- **Carries no secret and no bytes.** There is no credential field anywhere in the shape, and
  `.strict()` refuses a file that smuggles one in under any key; a connector's or a model
  connection's credential stays in the workspace it was entered into. A skill travels by name
  only — its bytes move with `skills.export`/`skills.import`, never with an agent.
- **Not carried:** run grants (`/grants`) name principals of one workspace and mean nothing in
  another, so they are left for the destination to decide.

`policy` is `AgentPolicySchema` verbatim: its skill allowlist and tool rules already speak
in names, and an allowlist may only name skills `resources.skills` assigns. The agent's engine
is `policy.engine`. `policySource` records whether the source agent's policy was stored
(`'stored'`, the default when a hand-written file leaves it out) or compiled from its
permissions and skills (`'compiled'`); import stores only a stored one, so a compiled policy
stays compiled in the destination. See ADR-0076 and spec 04 §6.2.

## AgentPolicySchema

The `GET`/`PUT /api/agents/:id/policy` payload (S-13). `engine` is the discriminant — the harness
that runs the agent loop, never the model provider (`runs.provider`, `MODEL_PROVIDERS`). There are
four arms — `'claude-agent-sdk'`; since ENG-09 (#308), `'openai-agents'`, whose engine-native
fields are two model settings and no tool grammar; since ENG-08 (#307), `'pi'`, whose only
engine-native field is a thinking level; and since ENG-10 (#309), `'mastra'`, whose only
engine-native field is a tool-call concurrency — and a route refuses any other value as
`400 unsupported_engine` rather than accepting and ignoring it.

The discriminant was called `provider` before ADR-0065, which is why a body carrying `provider`
is refused outright (`400 invalid_body`) rather than read as this shape: `provider` now means the
model provider everywhere else on the wire, and silently accepting it here would make one word
mean two things in the same request.

A `PUT`'d policy is **strictly narrowing**: the server unions the agent's permission-derived
tool denials and read-only file denials into `tools.deny` rather than replacing them, and
intersects `skills` with the agent's current skill assignments, so this policy can restrict an
agent past its permission checkboxes but never widen it past them. See
`docs/adr/SDK-02-AGENT-POLICY-234-stored-policy-is-a-narrowing-jsonb-column.md`.

**`GET` answers the base policy, not the effective one.** The body is the policy as stored, or —
for an agent nobody has `PUT` one onto — the policy derived from its permission checkboxes. Two
further layers are applied on top when a run is composed and are *not* reflected here: an
`mcp__<server>__*` auto-approval for every connector assigned to the agent, and
`Write(…)`/`Edit(…)`/`NotebookEdit(…)`/`Bash` denials for every read-only file grant. So
`tools.autoApprove` and `tools.deny` in this body are the base lists a run starts from, never
the full set a run ends up with; reading `autoApprove: []` does not mean no tool is
auto-approved at run time.

## CLAUDE_PERMISSION_TOOL_DENIALS

Which Claude tools each of §17 Step 4's four switches removes when it is off.

§6 maps "Tool permissions → allowedTools", and R-01 §10 established that this is incomplete:
`allowedTools` **auto-approves**, it does not restrict, so an agent whose `readFiles` is false
but whose tool surface still exposes `Read` can read files the moment a permission prompt is
answered — and a run with no interactive user has no one to answer it. So a switch that is off
maps onto `deny` (the SDK's `disallowedTools`), which removes the definition rather than
withholding an approval. `docs/adr/W1-COMP-01-permissions-map-onto-deny-not-allow.md` records it.

**This is a floor, not the finished §17 Step 4 mapping.** `AgentPermissionsSchema` is four
booleans and the SDK's surface is much larger; a fifth capability added to the checkbox set and
not here would be ungoverned. The compiler will not catch that — the record below is keyed by
`AgentPermissionKey`, so it *will* catch a key added to the permission set and not to this
table, which is the half a type can hold.

## Why this table is in `packages/contracts` and not in the Claude adapter (ENG-04b, #325)

The tool *names* are `@anthropic-ai/claude-agent-sdk`'s, so the natural home would be
`packages/engine-claude-agent-sdk` — and ENG-04b moved everything else about the Claude tool
mapping there. This table cannot follow, because it has a second caller the adapter cannot
serve: `GET /api/agents/:id/policy` answers the Claude arm of `AgentPolicySchema` for an
agent whose `policy` column is NULL, and `apps/web` may never import an engine adapter

one security decision, which is the drift this repository refuses. So the table lives beside the
Claude arm whose grammar it is written in, and both the control plane and the adapter read the
same one. `docs/adr/0072-the-claude-tool-mapping-and-skills-live-in-the-claude-adapter.md`

## claudeReadOnlyGrantDenials

The Claude denials that make read-only file grants read-only, for the run whose working
directory is `cwd`: one `Edit(//<cwd>/<path>)` rule per grant (`/**` added for a directory),
then `CLAUDE_GRANT_SHELL_DENIALS`.

Claude Code checks file writes against `Edit(path)` rules only — a `Write(path)` or
`NotebookEdit(path)` rule is accepted, never consulted, and warned about at startup — and only
`//path` is absolute: a single leading `/` anchors at the rule's settings source, so a rule
written as `Edit(<absolute cwd>/x)` would mean `<cwd>/<cwd>/x` and match nothing
(code.claude.com/docs/en/permissions, "Read and Edit"; R-01 §10). A Windows `cwd` is written in
the POSIX form Claude Code matches against, `C:\w` as `/c/w`.

Shared by the control plane's compose-side guard and the Claude adapter, which de-duplicate the
two into one list; both pass only the grants whose access is `read`.

```ts

```

## translatePolicyForEngineSwitch

Carry an engine switch's narrowing across (ADR-0074 D12, the Owner's decision on PR #339).

`previous` is the stored policy, `next` the one replacing it. When the two name the same engine
nothing is translated: a `PUT` replaces the policy, which is how an owner widens on purpose. When
the engine changes, whatever the old arm withheld is written into the new arm, so a switch can
never hand the agent a tool its owner took away:

| `claude-agent-sdk` said                                     | `openai-agents`, `pi` or `mastra` withholds |
| ----------------------------------------------------------- | --------------------------------- |
| `deny` of `Read`, `Glob` or `Grep` (bare or scoped)         | `readFiles`: the readers          |
| `deny` of `Write`, `Edit` or `NotebookEdit` (bare or scoped)| `writeFiles`: `apply_patch` / `write`, `edit` |
| `deny` of `Bash`, `BashOutput` or `KillShell` (bare or scoped) | `runCommands`: `shell` / `bash` |
| a `base` list missing any tool a switch governs             | that switch                     |
| `permissionMode: 'plan'`                                    | `writeFiles` and `runCommands`  |
| `permissionMode: 'dontAsk'`, a switch's tools not all in `autoApprove` | that switch          |
| `deny` of a tool this engine does not have (`WebFetch`, …)  | nothing: it stays absent        |
| `deny` of an MCP tool, an MCP glob or a wildcard            | **refused**                     |

A scoped denial (`Bash(git push:*)`) withholds the whole tool: this engine has no specifier
grammar, and the narrower reading is the safe one. The reverse switch writes each withheld
switch's `CLAUDE_PERMISSION_TOOL_DENIALS` into `tools.deny`, which is exact. Between
`openai-agents`, `pi` (ENG-08, #307) and `mastra` (ENG-10, #309) `withheldPermissions` is carried
verbatim.

The result never allows a tool the old arm denied: the Lean theorem
`AgentWorkspace.Theorems.Invariants.EngineSwitch.the_switch_never_widens_the_tool_plan` states
it, and `tests/formal/engine-openai-agents.test.ts` replays its `engine-switch.json` vectors
against this function. It is pure, so the route enforces it and `aw agents update --engine` can
show it before applying it.

```ts
translatePolicyForEngineSwitch(previous: AgentPolicy, next: AgentPolicy): EngineSwitchTranslation
```
