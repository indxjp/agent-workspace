Phase 3 · Agent Workspace gallery

How each use case is implemented, run, and turned into a benchmark

Every one of the ten gallery use cases goes through the same seven stages. The output is code under tests/gallery/<use case>/ that runs in CI with no API key, a tutorial page under docs/sdk/site/tutorials/, and a benchmark whose every verdict is backed by a test. A verdict can only change when a test changes, so the gallery cannot silently overstate what the SDK does.

The pipeline, per use case

Stages 1 to 5 and 7 run offline in pnpm test. Stage 6 needs a workspace and a model, so it is opt-in and is never reported as passed when it did not run.

Evidence: what backs a verdict

Each cell of a benchmark names one kind of evidence, and tests/gallery/benchmark.test.ts checks that the evidence exists: a test with that exact title, a probe with that id, a source file at that path.

How the work is split

One reference use case first, so the harness is proven before anything is copied from it; then nine in parallel, each owning only its own directory and page so no two workers touch the same file; then one integration step that owns every shared file.

done  Reference: harness + use case 1

  • Shared: MCP server kit (stdio and Streamable HTTP), Japanese bigram index, runAndRead, citation parser
  • Harness: project loader, MCP client, scripted workspace, probes, benchmark model, registry
  • Manual search: 6 tests, tutorial, generated table

done  Nine parallel workers

  • Each owns tests/gallery/<id>/ and tutorials/<id>.mdx, nothing else
  • Same pipeline, same harness; shared code changes go back to the integrator
  • Done means: its tests pass, tsc, eslint and prettier are clean, and the table is generated

done  Integration

  • docs.json navigation, llms.txt via pnpm docs:generate
  • pnpm check:fast, pnpm test, pnpm build
  • Update the gallery artifact with the verified verdicts

What the reference use case already found

Building the ten for real surfaced facts that reading the code in Phase 1 did not.

01

An eval cannot portably pin an MCP tool call

A Claude run names an MCP tool mcp__connector-<uuid>__search_manual, with the connector's id in that workspace (apps/web/server/compose/resource-loader.ts), and an eval's tool: is an exact match (apps/web/server/evaluations/score.ts). A committed tool: expectation is wrong in every other workspace. The gallery pins behaviour with contains instead.

02

A project file cannot declare a stdio MCP server

agent-workspace.yaml accepts only http/sse connectors (probe project-file-stdio). The gallery's server kit therefore speaks Streamable HTTP as well as stdio.

03

Bigram search needs a coverage floor to say "not found"

The first test run showed 「社員食堂の営業時間」 matching a maintenance interval through 「時間」 alone. The index now requires a third of the query's bigrams. Without the test, the agent's honest no-answer rule would never have fired.

04

Every backend rebuilds the answer from events

RunResource has no answer field, so the shared runAndRead follows the stream and keeps the last agent.message. Every use case needs it; it is the strongest argument for the structured-output gap.

05

Files an agent writes never come back

Verified with a live run: persistPaths collects the runner's /workspace, not the run's working directory (apps/web/server/runs/launcher.ts), so it promotes the stale hydrated copy. Filed as a separate fix task.

06

Agents as code cannot pre-approve the tools they are granted

defineAgent with writeFiles or runCommands compiles to permissionMode: 'default' with no auto-approval, and has no setting for either. An unattended run then refuses Write and shell commands. Six use cases need aw.agents.replacePolicy (probe define-tool-approval).

07

A surface cannot render an MCP tool's result

toolResults is matched exactly against the run's tool name, mcp__<connector-name>__… (or mcp__connector-<uuid>__… when the name is not a usable slug), which can differ per workspace and in the UUID form is over the 64-character key limit (probe surface-mcp-tool-results). The embedded widget also cannot carry who is signed in.

08

writeFiles: false does not stop shell redirection

Only the Write and Edit tools are denied (packages/contracts/src/agents.test.ts). With runCommands granted, a policy alone does not prevent file writes.
