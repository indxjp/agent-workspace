agent-workspace architecture

From .jevlint/architecture, compiled at d07c017e56c6d9cc9cb9aac6096c6dd93264d688.

Agent Workspace is a self-hostable platform for running AI agents for a team. The Next.js control plane (apps/web) holds workspaces, agents, sessions, files and runs, and launches each run on the runner (apps/runner), which places it in a sandbox through a runtime driver and executes it with one engine adapter (Claude Agent SDK, OpenAI Agents, Mastra or pi). Model calls go through the gateway, which swaps a short-lived run identity for the stored credential. Published packages (contracts, sdk, react, app, aw, cli) let browsers, the aw command line and customer apps reach the same /api/** contracts. Wire schemas sit at the bottom and depend on nothing; only packages/core talks to PostgreSQL and object storage.

Overview

Agent Workspace runs AI agents for a team, on infrastructure the team chooses. A workspace member defines an agent (instructions, model connection, files, skills, connectors, a runtime profile), talks to it in sessions, and shares it as a hosted chat surface, an A2A endpoint or a portal app. Developers drive the same platform from the aw command line, the TypeScript SDK or a generated project. The product is one control plane (apps/web), one runner (apps/runner), one gateway (packages/gateway) and a set of published packages under @indx-workspace/*.

The main workflow in one paragraph

A caller sends POST /api/agents/:id/runs. The route hands the request to startRun in apps/web/server/runs/api.ts, which authenticates the principal, checks run permission and starts an authorised, idempotent run: the run row is stored as queued in PostgreSQL through packages/core. The launcher then asks the runner's runtime manager for a sandbox and posts a RunRequest to ${base}/run over HTTP (launcher-execution.ts:76). Inside the sandbox the runner's runtime server (apps/runner/src/server.ts:259) checks the granted files' checksums, loads one engine adapter through apps/runner/src/engines.ts, and streams agent.* frames back as server-sent events. Every model call the engine makes goes to the gateway, which swaps the short-lived run token for the stored provider credential. The control plane stores the frames and settles usage and cost on the run.

Design principles

1. The wire contracts are at the bottom and depend on nothing

packages/contracts holds every /api/** schema, problem code and closed vocabulary, and imports only zod. The SDK, the browser screens, aw, the CLI, portal apps and the server all import the same schemas, and the SDK validates every response against them (ADR-0052).

  • Why: customers integrate from outside the repository, and a browser that reads a response differently from how the server renders it is a bug nobody sees.
  • Cost: a wire change is a contracts change, a regenerated API report and a lock-step release of nine packages (commit 4517e8bcf moved all nine from 0.6.12 to 0.6.13 together).
  • Kept by: the contracts component's empty depends_on, wire-packages-stay-framework-free, and dependency-cruiser's contracts-depend-on-nothing-in-the-workspace.

2. Only persistence talks to PostgreSQL and buckets, and a repository takes a tenant, not a caller

All database and object access is in packages/core. A repository's only request input is WorkspaceScope, a value minted from a lookup and deliberately without the actor or role (scope.ts:105-120). Inside the web server only a domain's store.ts should import core/db.

  • Why: tenant isolation is the first design priority in ENGINEERING_GUIDELINES.md; authorisation (RBAC) and tenant selection (scope) stay in different places with different reasons to change.
  • Cost: an extra store layer per domain, and 31 files that still name persistence outside a store (domain-does-not-import-persistence ceiling in tests/architecture-rules.test.ts).
  • Kept by: only-persistence-and-app-kit-use-drizzle, the three bucket only rules, the checklist item only-stores-name-persistence, and the repository's baseline ceilings.

3. Decisions are pure; effects come in as arguments

A domain's core/ folder imports only itself, the contracts and zod, and reads no clock, random value, environment, file or network (AGENTS.md, hexagonal rule 2). Outside cores, server code takes time from a Clock and ids from an IdGenerator.

  • Why: pure rules can be tested exhaustively and checked against the Lean model in formal/ (ADR-0062).
  • Cost: constructors grow clock and ids parameters (commit bd1d76148 threaded them through the Builder's shell and transport), and a ceiling of direct clock calls (pnpm clock:check) still has to be worked down.
  • Kept by: the checklist item domain-core-is-pure, dependency-cruiser's domain-core-is-pure and the ESLint globals ban.

4. One composition root, and a domain that can be off says so

apps/web/server/composition/register.ts reads the environment once, builds every domain and installs one ApplicationContext. A route reads it per request and answers its domain's named 503 when the domain is disabled or unavailable; there is no in-memory fallback.

  • Why: a half-composed process must never serve, and a missing runner or bucket must be visible to the caller.
  • Cost: application-context.ts imports a type from every domain, so the server's components form one cycle in the component graph (no-component-cycles reports it), and process-global state needs defineSlot because Next.js builds instrumentation and routes as separate module graphs.
  • Kept by: the checklist items one-context-install and environment-read-at-entry.

5. Engines, drivers and storage backends are plug-ins loaded only when chosen

The runner names engine adapters in one file and loads them with dynamic import() (engines.ts:60-65); each runtime driver is its own exports subpath; openObjectStore imports only the backend the storage URL names (packages/core/src/storage/index.ts:69-75).

  • Why: a local install must not load cloud SDKs, a run image must stay small, and a new engine must not touch the control plane (ADR-0065).
  • Cost: each adapter carries a conformance kit, and the single-file rules need their own tests (tests/no-sdk-import.test.ts).
  • Kept by: engine-sdks-stay-in-their-adapters, only-runtime-drivers-call-kubernetes, the runner's checklist item runner-reaches-adapters-through-engines-ts and one-sdk-file-per-engine.

6. Known violations are a baseline that can only shrink

Rules that the code does not yet meet are not loosened; their current violations are listed in .dependency-cruiser-known-violations.json and eslint-suppressions.json, and tests/architecture-rules.test.ts holds a ceiling per rule.

  • Why: a rule with exceptions that grow is not a rule.
  • Cost: the code carries visible debt for a long time, and every fix must also lower a ceiling.
  • Kept by: the ceilings test and CI's lint-baseline check. This SSOT follows the same idea: the imports against the context direction are left out of depends_on and reported, not allowed.

Published clients

sdk is the typed client every outside caller uses; aw-cli, react-chat, app-kit and the browser screens build on it, and none of them may reach a server package (docs/10-product/sdk/07-structure-map.md). project-cli generates and deploys projects, and aw loads its deploy and publish only through packages/aw/src/cli-bridge.ts. They hand work on by calling /api/** over HTTPS; the dashed arrow from the SDK to the routes is that boundary.

Control plane (apps/web)

web-routes is the Next.js tree; it renders web-ui screens and calls one domain function per route. The server is split into the bounded contexts that apps/web/server/contexts.json lists, upstream first: identity (with secrets), storage and sharing, execution, integrations, agents (with evaluations) and the store demo. In this SSOT they are the components identity, storage-sharing, execution, integrations, agent-authoring and store-demo, each allowed to depend only on the contexts before it. Each context has a public index.ts entry that the others should import. server-kernel is what all of them share, and composition builds them and installs the ApplicationContext they read at request time. The execution domain hands a run to the runner by HTTP, not by import.

Execution plane

runner is two processes: the runtime manager, which allocates a sandbox per session through one runtime-drivers driver, and the runtime server inside the sandbox, which runs one engine-adapters engine. Engines call gateway over HTTP with the run token. sandbox-tools are the tool host and egress proxy that run next to an agent; the tool host implements the tool-host contract from aw (intake.ts:25). embedded bundles the control plane, gateway and runner into one process for aw dev.

Contracts and persistence

contracts is the public wire language, run-contract the private one between control plane, runner and engines (AgentEngine, RunRequest), and platforms the pure translators that export a portable agent to other agent platforms. persistence (packages/core) is the only component that reaches PostgreSQL and object storage.

The layers run top to bottom. A component may import its own layer and those below. The server's contexts share the application layer because the composition root and the contexts import each other by design (the root builds them; they read the context it installed); their direction is held by each component's depends_on, not by layers.

How it runs

Start a run

POST /api/agents/:id/runs reaches startRun (apps/web/server/runs/api.ts:79). It reads the run domain from the application context and answers 503 if runs are disabled (no runner configured). It authenticates the principal, refuses a malformed agent id with 400 invalid_agent_id, resolves ownership, checks run permission, and calls startAuthorisedRun. The start is idempotent: an Idempotency-Key is stored per principal with the hash of the canonical request, so a replay returns the original run and a different request under the same key gets 409 run_idempotency_conflict (ADR-0151). Preflight and refusal mapping live in start-input, start-preparation and start-refusal.

The launcher then asks the runtime manager for a sandbox and posts the RunRequest to ${base}/run (launcher-execution.ts:76), carrying traceparent and a bearer token when one is set. relay.ts reads the SSE answer into stored frames; a status other than 200 fails the run with a public reason (relay.ts:312).

Interrupting a live run reaches only the replica that launched it (issue #261); orphaned runs are failed by the stale sweep under a database lease.

Execute a run in the sandbox

The runtime server inside the sandbox accepts POST /run and its alias /invocations (apps/runner/src/server.ts:259). Admission parses the RunRequest, resource verification checks every granted file's size and checksum against the archive the control plane streamed, and run-execution.ts starts the engine that engines.ts loads by dynamic import. An engine whose package is not in the image answers engine_not_installed (comment above ENGINE_MODULES).

Boot the control plane

Next.js calls register() once per server process (apps/web/instrumentation.ts). register.ts reads settings and opens the database, then registerOpenedDatabase calls the wire<Domain> functions and finally installApplicationContext once. If wiring throws, nothing is installed and the pools opened so far are closed (docs/architecture.md:313-331).

How a save stays consistent

Every save is row-first (ADR-0153). The catalog reserves a pending row under a new object id, streams the bytes to workspaces/<workspace id>/<area>/<object id>, then one transaction confirms the row as ready with the measured size and checksum. A replaced or removed row is deleting until its object is gone, and a cleanup job reports or removes what a crash left. Only ready rows are listed, searched or granted, and a rename changes the row alone.

Runs

A run row's status comes from the closed vocabulary in packages/contracts/src/runs.ts. A paused run (awaiting_approval) stores a deadline 24 hours ahead; one unique index allows exactly one continuation per paused run, and approved tool calls are consumed by one guarded update so each runs at most once (docs/architecture.md:597-622). Usage, tokens and cost are written on the run row (RunRecord: inputTokens, costUsd, accountingState).

Tenancy

Every repository query is built from WorkspaceScope.workspaceId, a value the scope resolver mints from a lookup. The class keeps a private copy so isWorkspaceScope can check an invariant rather than a shape (scope.ts:105-120). Authorisation happens before a workspace-scoped read.

Lifetimes

Sign-in session cookies last 12 hours, CLI tokens 12 hours, browser tokens 1 to 60 minutes, run tokens 5 minutes (at most 1 hour), public share links 24 hours to never; bearer secrets are stored only as SHA-256 hashes. Migrations under migrations/ are forward-only and expand/contract (pnpm migrations:lint). Demo workspaces, their tokens, admissions and guests are swept when they expire (store-demo).

Cross-cutting concerns

Errors

Every owned JSON route builds its { error: { code, message } } envelope in apps/web/server/http/result.ts, rendered by route() in http/route.ts; the comment at the top of result.ts lists the deliberate variants (public surface pages, versioning). Expected failures carry a stable code from packages/contracts; infrastructure failures stay 5xx, keep their cause for the log and never echo SQL, provider or credential text (checklist expected-failures-are-typed). The SDK decodes the envelope into typed errors such as ApiProblemError.

Trust boundaries and access

A request is checked three times, each for one thing: apps/web/proxy.ts checks that a credential of the right shape is present and a cookie is validly signed; the route resolves the credential into a Principal (resolveActor, composition/session-rbac.ts); decide() in rbac/decide.ts asks the pure rules in rbac/core/ whether that role may use the method on the path. Signing keys derive from SESSION_SECRET with HKDF and a purpose label, so a token for one purpose fails every other. Only identity imports jose and openid-client (only-identity-verifies-oidc).

Provider credentials never reach a sandbox. The runner receives a short-lived run token signed with GATEWAY_TOKEN_SECRET (packages/gateway/src/tokens/run-token.ts), and the gateway swaps it for the stored key. Sandbox egress goes through packages/egress-proxy, which refuses loopback, private, link-local (including the cloud metadata address) and reserved ranges (address.ts).

Input validation

HTTP bodies, provider JSON, environment values, persisted JSON and runner frames are unknown until a Zod schema or a small predicate checks them. Owned APIs reject unknown keys; extensible third-party protocols may keep them after the consumed fields are validated.

Configuration

The environment is read once, in a composition root or a process entry point, and passed on as typed values (checklist environment-read-at-entry). The files that still read process.env elsewhere are the no-restricted-properties entries of eslint-suppressions.json, which may only shrink. AW_STORAGE_URL is the one storage setting, parsed by parseStorageUrl for server and CLI alike.

Observability

Web, runner and gateway log one JSON object per line through the Logger port in @agent-workspace/core/telemetry, with fixed msg strings and redacted values. A W3C traceparent travels from the web's span to the runner and on to the gateway with every model call; OpenTelemetry export is on only when OTEL_EXPORTER_OTLP_ENDPOINT is set (ADR-0155). Only persistence and the web's server-kernel telemetry import OpenTelemetry.

Concurrency

Run start is idempotent per key; approvals are consumed by guarded updates; catalog locks are proven on PostgreSQL only. The stale-run sweep runs on one replica at a time under a database lease, and interrupts reach only the launching replica.

Decisions

The SDK is contracts-first and the application is its first consumer (ADR-0052)

  • Context: /api/** contracts lived as hand-written parsers inside server domains, so nothing outside the repository could validate against them.
  • Decision: contracts publishes Zod schemas and depends on zod alone; sdk depends only on contracts. A domain enters the SDK only after a conformance test proves the server's real serializers satisfy the schema, and apps/web/contracts re-exports rather than copies.
  • Consequences: browser screens reach the server only through the SDK; a wire change is a versioned, reported change.
  • Alternatives: generating the client from OpenAPI (no document existed, and it would lack the stream follower); publishing apps/web/contracts directly (breaks "packages never import apps"); moving every domain at once (would freeze open defects into a public surface).

An agent's engine is an extension point behind one port (ADR-0065)

  • Context: every agent ran on the Claude Agent SDK, imported from one runner file; the Owner decided on 2026-09-26 to accept other engines.
  • Decision: the platform owns the AgentEngine port in packages/engine; each engine is a packages/engine-<id> adapter with one SDK file, reached by the runner only through apps/runner/src/engines.ts. "Provider" keeps meaning the model provider; the harness is the "engine".
  • Consequences: four adapters exist (Claude Agent SDK, OpenAI Agents, Mastra, pi); the control plane knows engines only by id.
  • Alternatives: keeping the Claude SDK as the only runtime, which the earlier spec required and this ADR reversed.

Object storage: one key layout, catalog-first writes, references not bytes (ADR-0153)

  • Context: three object roots, path-as-key renames, rows written after objects under an in-process lock, and granted files base64-encoded into the /run body.
  • Decision: one object store and key layout with immutable object ids, row-first saves, a streaming ObjectStore port in packages/core/src/storage, and runs that receive references and one streamed archive.
  • Consequences: a rename touches one row; a crash leaves only rows the cleanup job can see.
  • Alternatives: a new packages/storage, path-as-key, object-first writes, and a maintenance-window migration were all rejected.

The local runtime is one bundled package that aw dev forks (ADR-0109)

  • Context: aw dev must run control plane, gateway and runner in one process from a generated project, but the server was not installable.
  • Decision: @indx-workspace/embedded bundles them over embedded PostgreSQL; nothing imports it.
  • Consequences: embedded is the only component allowed to depend on almost everything.
  • Alternatives: bundling the server into aw or the CLI, an all-in-one container image, downloading the runtime on first run, and publishing core, gateway, runner and web separately.

The server is split into bounded contexts with public entries (refactoring plan part 04)

  • Context: apps/web/server grew to dozens of domain folders importing each other freely.
  • Decision: contexts.json groups the folders into contexts listed upstream first, a shared kernel and the composition root; dependency-cruiser builds one direction rule and one entry rule per context from the data (commits 21932f40f for identity, 65dde8faf for execution).
  • Consequences: the existing contrary imports became baselines that can only shrink; moving a folder between contexts is a one-line data change.
  • Alternatives: not recorded in the commits or the architecture document; splitting the server into packages is not discussed there.

RBAC's rules are pure and live in rbac/core (commit 754f81e5d)

  • Context: roles, scopes, the permission table and the decision were mixed with path classification and I/O.
  • Decision: move them into apps/web/server/rbac/core/ under both purity checks; rbac/decide.ts classifies the path and passes the verdict in.
  • Consequences: the authorisation rules can be tested and checked against the formal model without a server. Alternatives are not recorded.

Run start is idempotent and a stopped run holds no lease (ADR-0151)

  • Decision: ratify awaiting_approval as a stopped, lease-free status and keep waiting and suspended out; a start replay with the same key and request hash returns the original run.
  • Alternatives: the ADR's other options, including persisting a live waiting state, which it rejects because it creates recovery obligations with no producer.

A public share link is shown once and stored only as a hash (commit a75871d09)

  • Decision: POST /api/shares returns the token once; the server keeps its SHA-256, migrated expand-only (migration 0105) with a trigger for rolling updates.
  • Consequences: a lost link cannot be shown again; aw shares list has no URL column. Alternatives are not recorded.

Risks and debt

The server's contexts form one cycle

jevlint architecture check --static reports a single component cycle through composition, server-kernel and every server context. Part of it is by design: application-context.ts imports a type from every domain (lines 15-39) and every domain reads applicationContext(). Hubs

jevlint architecture plan ranks the contracts barrels (agents.ts, agent-versions.ts, project-file.ts, surfaces.ts, setup.ts) as hubs used by up to 16 components. They are deliberate public surfaces listed by name, so a change to one fans out to every client; the API reports in docs/10-product/sdk/api/ make that visible. In packages/core, repositories such as agents.ts, agent-versions.ts and directory.ts are hubs inside persistence.

Persistence outside stores

31 files in apps/web/server still name core/db outside a store.ts (domain-does-not-import-persistence). This SSOT cannot check it, because the rule is per file inside a component; it is the checklist item only-stores-name-persistence.

Layer exceptions this SSOT accepts

  • sandbox-tools sits in the delivery layer because the tool host imports the tool-host contract type from @indx-workspace/aw/tools/host (packages/tool-host/src/intake.ts:25).
  • agent-authoring imports gateway (evaluations) and sdk (the Builder's definition), so the control plane depends on two packages beside core.

Hard to change

  • apps/web/server/runs/api.ts is named as the largest unit still due to be split (docs/architecture.md:706).
  • Interrupt is per replica (issue #261), and there is no run-attempt row or renewable launch lease.
  • Runner, gateway and web each have bare durations and direct clock calls counted by pnpm durations:check and pnpm clock:check.
  • Test code is mixed into source folders (*.test-support.ts, *.contract.ts, conformance suites, acceptance harnesses); this SSOT ignores them by pattern, so a production file with such a name would be missed.

What surrounds Agent Workspace

People and programs come in through the control plane; only the runner touches sandboxes and only the gateway touches model providers.

Arrows
  • Workspace member → Control plane: uses the console
  • Developer or CI job → Control plane: calls the API
  • Surface or app visitor → Control plane: chats on a surface
  • External A2A agent → Control plane: sends A2A tasks
  • Control plane → PostgreSQL: reads and writes
  • Control plane → Object storage: streams files
  • Control plane → OIDC identity provider: verifies ID tokens
  • Control plane → Runner: posts /run
  • Runner → Sandbox platforms: allocates sandboxes
  • Runner → Model gateway: model calls
  • Model gateway → PostgreSQL: reads credentials
  • Model gateway → Model providers: forwards calls
  • Model gateway → Control plane: forwards aw-control
