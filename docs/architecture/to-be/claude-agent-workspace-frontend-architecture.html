Target screen inventory and ownership

Existing routes stay unless a missing product journey requires a route. Select a screen to see its desired shell, feature, state and API boundaries.

Target dependency graph

Dependencies point inward: Route → Feature screen → Feature hooks/client → shared HTTP/contracts. Shared UI never imports features; feature modules do not import sibling internals.

State and component ownership rules

Server state

Feature clients parse their own wire schemas through one apiClient. Feature hooks own loading, cancellation, refresh and mutation invalidation. Cache keys always include workspace identity; full workspace navigation remains the hard reset.

Local UI state

Dialogs, draft text, expanded panels and selection baskets remain component-local or in a feature reducer. They are never placed in a global domain store.

Forms

One feature schema drives draft validation and request mapping. Server validation remains authoritative; per-step validation prevents impossible wizard progression without duplicating policy.

Resource selectors

features/resource-assignment is a stable shared concept—not a generic resources bucket. It provides typed File/Skill/Connector pickers to Agent, Project and Composer features.

UI primitives

components/ui owns Page, PageHeader, Button, Card, Alert, Dialog, StatusBadge, Timestamp and Icon. Primitives know no domain entity or API.

Icons/assets

Extend the existing typed React SVG registry into one icon module. Feature code consumes named icons; raw path data and Unicode action glyphs do not live in screens.

Target assessment

Design constraint. This is a structural refactoring, not a visual redesign. The shell, one RunView, URL-backed filters, server components where useful, and hard tenant navigation remain. A server-state library is not mandated; introduce one only if the small shared client/hook contract proves insufficient.
