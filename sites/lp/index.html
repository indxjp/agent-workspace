Agent Store

agents you can run today. on the shelf, across areas of work.

This section shows the store's live agents, one tab per area of work. Every card is a real agent with its own sample data: open it, sign up with your email, and it runs in a demo workspace of your own. The last card of a tab counts the agents still on the way.

The store is a preview. The cards, names and counts on this page are read from its catalog when the site is built.

How the store works

Browse, try, customize, install. The way you get an app, for an agent that runs on your servers.

These are the four steps from a store listing to the agent running in your own environment, and what you see at each one.

  1. 1

    Browse

    Every listing says what the agent does, what it reads, which systems it connects to and how it behaves, before you try it.

    You see: the listing below
  2. 2

    Try it on sample data

    Sign up with your email. The real agent runs on fictional sample data in a demo workspace of your own, for a limited time. You watch its tool calls and its result, not a video.

    You see: the run, as it happens
  3. 3

    Customize

    See it set up for your company: The preview changes as you type, and your setup travels with your enquiry.

    You see: your version of the agent
  4. 4

    Install into your own cloud

    The agent is a folder of files you can read on GitHub. Add them to your project and deploy with the aw CLI to your VM, Google Cloud Run or Kubernetes, or ask INDX to set it up with you.

    You get: the agent, in your repository

What “install” means here

Nothing is installed into someone else's cloud. Your project holds the agent's files; the aw CLI checks them, saves a version in your workspace and deploys the workspace to infrastructure you run. Chapter 1 of the docs creates the project; chapter 5 ships it.

Chapter 1: Run your first agentChapter 5: Ship it
# 1 · your project, once
$ npm create @indx-workspace@latest my-agents -- --yes
# 2 · add the agent's files from its source folder
$ cd my-agents && npx aw check
# 3 · save a version, deploy to your infrastructure
$ npx aw push --yes
$ npx aw deploy production --plan
$ npx aw deploy production --yes
Every agent has a label

Know what an agent reads and may change before you run it, the way an app shows its privacy label.

This is a real listing from the store, the one it features on its home page, built from the catalog entry for that agent.

  • What it readsThe documents and records the agent looks up. In the demo they are fictional; in your workspace, only the folders and connectors you grant.
  • Systems it connects toEach one is a connector you configure, with its credential kept as a secret the agent never sees.
  • How it behavesWhat the platform enforces, not what the prompt promises: whose rights a tool call uses, and which writes wait for a person.
  • What you can customizeThe settings that change for your company, shown on the listing's Install & customize tab.
  • SourceThe folder that holds the agent, in a public repository. What you try is what you install.

Very little code

A business app in a few hundred lines. An agent in about a dozen.

The bars count the lines a person wrote in each example app of the store, as the apps benchmark measures them, against the budget each app is held to. The data model, screens, API and the agent's tools are generated.

import { defineAgent, mcp } from '@indx-workspace/sdk/define';

export default defineAgent({
  name: 'writer',
  description: 'Works with pages in the wiki app.',
  instructions: [
    'You work in the wiki app for the person who asked, through its tools:',
    'pages: page_list and page_get read them, page_search finds them when the resource is searchable, and page_update changes the fields agents may write.',
    'Each tool acts as that person, so it refuses what they may not do; say so instead of retrying.',
  ].join('\n'),
  tools: [mcp('wiki')],
});

The wiki app's writer agent, as npx aw generate agent writer --tools page wrote it. mcp('wiki') is the app's connector: its tools come from the app's resources and act as the person who asked.

In what order

From the first command to production, in seven chapters.

This is the order the docs teach. Each step links to its chapter and says what you have working at its end; chapters 2 and 3 are a loop you repeat until the agent is good enough.

  1. 1Run your first agentOne command, no Docker. An agent answering on your laptop in about a minute.
  2. 2Build your agentInstructions, engine, model, skills, tools and credentials, as files you commit.
  3. 3Test and improve itRead each run's tool calls and cost, and keep an eval suite for local runs and CI.
  4. 4Put it in your productA hosted page, a script tag, React, your backend or plain HTTP.
  5. 5Ship it to your serversDeploy, push and promote to a VM, Google Cloud Run or Kubernetes.
  6. 6Run it for your teamRoles, workspaces per environment, shared agents and an audit trail.
  7. 7Run it on other platformsOptional: export to a hosted agent platform, with a report of what it keeps and drops.

import { builtinSkill, defineAgent, files, skill } from '@indx-workspace/sdk/define';

export default defineAgent({
  name: 'manual-search',
  instructions: { file: './manual-search.md' },
  model: 'default',
  // A run is unattended: without autoApprove the SDK stops the tools' calls on an approval prompt.
  engine: {
    id: 'claude-agent-sdk',
    autoApprove: ['mcp__agent-workspace__run_skill_script', 'mcp__agent-workspace__search_files'],
  },
  // Read-only by construction: it searches the manuals with the platform's `search_files` and
  // reads the PDF through office-reader, nothing else. The portal narrows each run to the manuals
  // the signed-in person may read (`runs.start({ fileScope })`). `runCommands` is what offers
  // `run_skill_script`; no write, no network.
  permissions: { readFiles: true, runCommands: true },
  skills: [builtinSkill('office-reader'), skill('cite-answer')],
  files: [files('manuals', 'read')],
  limits: { maxTurns: 12, maxBudgetUsd: 0.5 },
});

backend/ask.ts
// runAndRead is the manual-search tutorial's own helper, not an SDK export
export async function askManual(aw, agentId, question, subject, sessionId?) {
  const fileScope = fileScopeFor(subject);                      // the manuals data/access.json lets them read
  if (fileScope.length === 0) throw new NoManualAccess(subject); // no run at all
  const reading = await runAndRead(aw, agentId, { prompt: question, subject, fileScope, sessionId: sessionId ?? null }, ManualAnswerSchema);
  const found = new Set(
    reading.toolCalls
      .filter((call) => toolIs(call.name, 'search_files') && !call.isError)
      .flatMap((call) => foundIn(call.output ?? '')),
  );
  const { answer, citations } = reading.output;                  // typed, not parsed
  const unverified = citations.filter((citation) => !found.has(keyOf(citation.source, citation.page)));
  return { answer, citations, unverified,
           grounded: citations.length > 0 && unverified.length === 0, … };
}

      From laptop to production
      
Five commands. The same agent all the way through.

    

    

      
    
        
  1. Scaffold and run
    A starter project with an agent and a surface, running in one Node process with embedded PostgreSQL. No Docker.
    2. 
        
  2. Talk to it
    Interactive aw chat streams the answer with a line per tool call, so you see what the agent did, not just what it said. -p prints only the answer.
    3. 
        
  3. Score it
    aw eval runs evals/<agent>.yaml and stores the score. A thumbs-down from a real user becomes a new case with aw eval add-case.
    4. 
        
  4. Version and promote
    aw push --yes saves a version. On aw dev, aw promote moves production to it only if the score clears minEvalScore; aw rollback moves it back.
    5. 
        
  5. Deploy
    aw deploy production --plan shows what will change; --yes applies it to a single VM or Cloud Run.
    6.

Legal
Contract review agent
Legal uploads a counterparty's Word draft; the agent splits it into 第N条 clauses, compares each with the playbook and standard clauses, and…

          
import { builtinSkill, defineAgent, files, skill } from '@indx-workspace/sdk/define';

export default defineAgent({
  name: 'contract-review',
  instructions: { file: './contract-review.md' },
  model: 'default',
  // A run is unattended: without autoApprove the SDK stops the skill script's call on an approval prompt.
  // The one thing legal decides is the redline: the agent saves it with `Write`, and the run waits
  // there for an approval (ADR-0145) before the Word file is made. Every other file is written by a
  // script, so that `Write` is the run's only gated call.
  engine: {
    id: 'claude-agent-sdk',
    autoApprove: ['mcp__agent-workspace__run_skill_script', 'mcp__agent-workspace__search_files'],
    requireApproval: ['Write'],
  },
  // office-reader turns the draft into paragraphs JSON in `drafts` (the one read-write scratch
  // grant); contract-playbook checks that JSON, and once legal approves the redline, office-reader
  // writes the redlined copy to `outputs/` (the folder the run collects; the backend reads it back
  // with `runs.outputs`). It reaches no network. `runCommands` is what offers `run_skill_script`.
  // A question about a playbook rule is answered with the platform's `search_files` over the granted
  // `playbook` folder: no index and no connector of ours.
  permissions: { readFiles: true, writeFiles: true, runCommands: true },
  // Pinned to revision 1 of the playbook (`aw skills publish`): each review's run names this
  // version, and the version names the rules that applied, so a later edit cannot change the answer.
  skills: [builtinSkill('office-reader'), skill('contract-playbook', { revision: 1 })],
  files: [files('contracts', 'read'), files('playbook', 'read'), files('drafts', 'read-write')],
  limits: { maxTurns: 20, maxBudgetUsd: 1 },
});

    id: 'claude-agent-sdk',
    autoApprove: ['mcp__agent-workspace__search_files'],
    handoff: true,
  },
  // It reads the FAQ (the one granted folder) with the built-in `search_files` and the customer's
  // history through the read-only CRM tool; no write, no command, no network, no server of ours.
  permissions: { readFiles: true },
  tools: [crm],
  skills: [skill('keigo-reply')],
  files: [files('faq', 'read')],
  limits: { maxTurns: 10, maxBudgetUsd: 0.3 },
});

Ringi review agent

import { workflow } from '../tools/workflow.ts';

export default defineAgent({
  name: 'ringi-review',
  instructions: { file: './ringi-review.md' },
  model: 'default',
  // A run is unattended: without autoApprove the SDK stops the file search on an approval prompt.
  engine: { id: 'claude-agent-sdk', autoApprove: ['mcp__agent-workspace__search_files'] },
  // It reads the rules and the archive, and its one write is a comment on the ringi (postComment,
  // which waits for approval). It cannot approve or reject a ringi because no tool it holds can,
  // and the project's policy ceiling forbids writing files, running commands and open network
  // access for every agent in the project. The rules and the past ringi are found with the
  // built-in `search_files`; the backend narrows a run to the departments' folders the filer may
  // read (`runs.start({ fileScope })`).
  permissions: { readFiles: true },
  tools: [mcp('authority'), workflow],
  skills: [skill('ringi-checklist')],
  files: [files('rules', 'read'), files('ringi', 'read')],
  limits: { maxTurns: 16, maxBudgetUsd: 0.5 },

      FAQ
      
Questions buyers ask first.

      
Something else? Ask us.

    

    

      
What is the Agent Store?
A catalog of business agents, grouped by area of work. The live ones run for real: sign up with your email and the agent works on fictional sample data in a demo workspace of your own, for a limited time. Each listing also shows how the agent would be customized for your company and links to its source. The store is a preview today.

      
How do we install an agent from the store?
An agent is a few files: its definition, its skills and its settings. Add them to an Agent Workspace project, check them with aw check, save a version with aw push and deploy with aw deploy to your own VM, Google Cloud Run or Kubernetes. Or ask INDX to set it up with you, starting from the setup you chose on the listing.

      
Is this another agent framework?
No. The engine you choose runs the agent loop, unchanged: the Claude Agent SDK by default, or Mastra, the OpenAI Agents SDK or pi. Agent Workspace stores what an agent is, secures its credentials, launches it in the sandbox you chose and streams what it did.

      
Does any data leave our infrastructure?
The control plane, runner, sandboxes, database and object storage all run where you deploy them. The only outbound traffic an agent needs is to the model provider you configure, through the gateway, and the network policy of each runtime decides the rest.

      
Can we use Azure OpenAI or OpenAI instead of Claude?
Yes, through the Anthropic-compatible gateway. It is a compatibility mode, not an equivalent: each provider adapter declares what it supports (Azure OpenAI declares neither prompt caching nor thinking), and the agent editor warns when the chosen model lacks prompt caching. See compatibility.

      
Which sandboxes are production-ready today?
Docker is the recommended runtime for self-hosting and is fixture-verified. The sandboxed-process and Kubernetes drivers are implemented; Kubernetes lifecycle is partially verified. Azure Container Apps sessions and Cloud Run are implemented but not live-verified, and the rest are on the roadmap. The product disables what is not ready and says why.

      
Do we need Kubernetes?
No. A laptop needs one Node process. A single VM runs five components from one Compose file. Kubernetes is there when many teams need stronger isolation.

      
What happens if we stop using it?
You keep everything. Skills are SKILL.md folders, agents are TypeScript files or SDK options, connectors are MCP servers. Nothing is stored in a proprietary format.

      
Is there RAG or a vector database?
Deliberately not. Agents read workspace files with the SDK's own file tools and reach your systems through MCP connectors. Fewer moving parts to operate.

      
How do we buy it?
The SDK and CLI packages are published on npm. For a deployment, the Helm chart and support, book a demo with INDX.
