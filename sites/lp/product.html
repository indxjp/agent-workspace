The solution

Keep the Claude Agent SDK. Add the layer around it.

Agent Workspace never replaces query(). It stores what an agent is, secures the credentials it needs, launches it inside the sandbox you chose, and streams what it did back to a browser. The Claude Agent SDK is the default engine. Three promises: managed agents in your own cloud; you build the agent and the rest is one API call; switch the model or the runtime and embed anywhere.

Everything you clicked compiles into ordinary SDK options.

There is no intermediate agent abstraction. The platform's job is to turn database rows into this object, and then get out of the way. 

const options = {
  cwd,                  // the hydrated /workspace for this session
  model,                // step 01 — model connection
  mcpServers,           // step 03 — connectors
  skills,               // step 02 — materialised as skills/<name>/SKILL.md for the session
  disallowedTools,      // step 04 — a permission that is off removes its tools
  allowedTools,         // step 03 — each connector auto-approved as mcp__<connector-name>__*
  maxTurns,             // set in code or the SDK
  maxBudgetUsd,         // set in code or the SDK
  settingSources: ["project"],   // the session's own project only, never host user state
  strictMcpConfig: true, // only the connectors this agent was given
  env,                  // a gateway token for this run, never a provider key
};

for await (const event of query({ prompt, options })) {
  // stream event to the UI
}

Upgrades stay boring

The SDK is an upstream dependency, pinned and tested — not something copied into this repository. All SDK-specific translation is concentrated in one small module, so an option change upstream touches a handful of files. The same project can also run on the openai-agents, pi or mastra engines when their runtime image is installed; the Claude Agent SDK stays the default.

Skills stay portable

The stored representation is Claude's native SKILL.md directory. Import an existing skill folder with aw skills import or the SDK, edit it in the UI, export it back out with aw skills export.

skills/ └── invoice-review/ ├── SKILL.md └── supporting-files/

What you manage

The whole surface an Agent SDK deployment needs. Nothing else.

Twelve objects a company actually has to manage around the SDK — and every one of them is editable by a person who has never opened a terminal. Developers get the same objects as code, below.

Ship an agent without writing code

Name, instructions, model, capabilities, permissions, runtime. Five screens, then Deploy.

agents

Point agents at any model

Anthropic, Azure OpenAI, OpenAI or any compatible endpoint. Switching is a dropdown, not a refactor.

model_connections

Give agents your documents

Upload files and create folders, assign them per agent, read-only or read-write. Not RAG, not embeddings — workspace files the SDK's file tools can read.

files

Reuse Claude skills as-is

Create and edit skills in Claude's native format in the browser, import and export them with the CLI or SDK, then assign them to agents.

SKILL.md

Connect internal systems

MCP servers over HTTP or SSE, added through a short form, or read-only OpenAPI tools run by the gateway. No raw JSON to edit.

mcpServers

Decide what an agent may do

Read files, write files, run commands, reach the internet: four switches. One that is off removes its tools from the model.

disallowedTools

Choose where it runs

One driver interface: local, sandboxed process, Docker and Kubernetes run today; two managed-cloud drivers are implemented and awaiting live proof. The agent never changes.

RuntimeDriver

Resume long conversations

Session state lives in PostgreSQL and object storage. When a run was durable, a fresh sandbox is hydrated and the session resumes where it stopped.

sessions

Keep credentials out of agents

Provider keys are resolved only by the gateway. A sandbox gets a short-lived token bound to one run and one model; secrets are write-only.

secrets

Give the right people the right access

Four roles: Owner, Admin, Builder, Viewer. Viewers run only the agents they are granted. Enterprise SSO through any OIDC issuer.

memberships

Automate from CI

Workspace API keys, each with one role and an optional expiry, used from the TypeScript SDK or the aw CLI on a server. The secret is shown once; keys never go to a browser.

api_keys

Answer "who changed what"

21 audited actions, from permission and credential changes to agent edits and runtime switches. Owners read the trail; no secrets in it.

audit_events

No vector database. No RAG pipeline. No workflow canvas. Adding those would make this harder to operate, not more useful.

Runtimes

Pick where agents actually execute. Change your mind later.

The same agent definition runs on a laptop, on one Docker host or on your Kubernetes cluster without changing the agent, the skills, the connectors, or any application code. Only the selected runtime changes. Managed-cloud sandboxes sit behind the same interface; none has a live isolation proof yet, so they are marked below as they stand.

What survives a runtime switch

✓

Workspace files — object storage is the source of truth, the new sandbox is hydrated

✓

Skills and connectors — materialized into the workspace at launch

✓

The session, when its run was durable: stored, then resumed with resume

✕

Anything else in the old sandbox — sandboxes are disposable by definition

If switching a runtime requires editing the agent, the abstraction has failed and the driver is wrong — not the agent.

Compatibility, honestly

We tell you what does not work.

A non-Claude model behind an Anthropic-compatible endpoint is a compatibility mode, not an equivalent. Every model provider declares capability flags, and every runtime declares the network policies it can enforce. Today the agent editor warns in plain language when the chosen model lacks prompt caching, and a runtime refuses a policy it cannot enforce.

CapabilityClaudeAzure GPTOpenAI
Streaming✓✓✓
Tools✓✓✓
Thinking✓−✓

The flags each gateway adapter declares today. Claude prompt caching stays undeclared until a live replay verifies it. A provider compatibility suite exists and the adapters are fixture-verified; live-provider results are not yet published. See models and runtimes.

Never silently claim 100% compatibility. Never silently downgrade a guarantee.
