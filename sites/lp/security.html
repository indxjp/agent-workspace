Where your data lives

Five services in your infrastructure, one public port.

A full deployment is five services. Only web is exposed, on port 3000, and you put your own TLS terminator in front of it. Sandboxes are created on demand by the runtime driver; they are not a sixth service.

ServiceDoesExposed
webThe UI, /api/**, authentication, the setup wizardPort 3000, the only public one
gatewayThe model gateway. Substitutes a per-run token for the stored provider credential; Anthropic-compatible /v1/messagesPrivate; reachable from sandboxes
runnerAllocates a sandbox through the chosen runtime driver and relays the agent's events. The Docker socket is mounted here and nowhere else.Private
postgresPostgreSQL 17. Every durable row: workspaces, principals, agents, runs, eventsPrivate
storageSeaweedFS, S3 or GCS. Workspace files, skills, transcriptsPrivate

Three stores, one each

PostgreSQL

Every durable row the control plane has, including the session row.

Object store

Files, skills and transcripts, in SeaweedFS, S3, GCS or Azure Blob.

Secrets, inside PostgreSQL

Envelope-encrypted under one deployment key, not a fourth store.

These stores hold Agent Workspace's own state. Your own databases and document systems reach an agent only as an MCP connector or as uploaded files. Native object-store and secret backends per cloud are implemented, with live proof pending; see the data plane.

Credentials

Credentials never enter a sandbox.

The agent runs in the sandbox, but the key that pays for its model calls stays with the gateway. What the sandbox gets is a token that is only good for one run and one model.

Gateway-resolved provider keys

Provider credentials are stored encrypted and resolved only by the gateway.

gateway

A run- and model-bound token

Inside the sandbox, the provider key is replaced by a short-lived token bound to one run and one model.

per-run token

The run environment refuses provider keys

The compiled run environment refuses ANTHROPIC_API_KEY outright; the run is not compiled.

ANTHROPIC_API_KEY

Write-only secrets

Secrets, connector credentials and runtime credentials are write-only over HTTP. Only an Owner may delete a secret.

write-only

Envelope encryption and key backends

Secrets are envelope-encrypted inside PostgreSQL under one deployment key. The deployment key can come from a cloud key service. Three backends exist; only one has a live proof.

Key backendStatus
Azure Key Vaultverified

Isolation, per runtime

Isolation depends on the runtime, and we say which is proven.

A runtime profile names one of eleven driver ids. Six are implemented. Only docker is fixture-verified, and no managed-cloud driver has a live isolation proof yet.

DriverIsolationStatus today
localNone. Development only.no isolation implemented, dev only
sandbox-runtimeHost OS sandbox. On Linux it needs bubblewrap, socat and ripgrep.implemented
dockerOne container per session. The single-VM default.fixture-verified

Network policy, enforced or refused

none

The model gateway only. The profile grants the sandbox no other network destination.

restricted

The gateway plus the profile's allowedDomains, on a driver that can enforce them.

open

Everything. Choose it deliberately.

✕ A policy the driver cannot enforce is refused.
The server answers 422 network_policy_not_enforceable rather than pretending.
⚠ docker refuses restricted; kubernetes refuses allowedDomains.
Docker refuses restricted and any allowedDomains, so in practice it is none or open. There is no proxy setting to change that today.

Least privilege for agents

A permission that is off removes its tools.

Each agent has four permission switches. When a switch is off, the compiled Claude Agent SDK options deny its tools through disallowedTools. Withholding an approval is not enough, because allowedTools grants and does not restrict.

Switch offTools denied
readFilesRead, Glob, Grep
writeFilesWrite, Edit, NotebookEdit
runCommandsBash, BashOutput, KillShell
unrestrictedNetworkWebFetch, WebSearch
  • Connectors assigned to the agent are auto-approved as mcp__<connector-name>__*, and only those: strictMcpConfig: true.
  • Host .claude settings are never inherited: settingSources: ["project"] loads only the session's own project, never user or local.
  • A read-only file grant denies Write, Edit and NotebookEdit on that path, and any read-only grant denies the shell tools, since a shell redirect could write anyway.
  • A project policy can set a ceiling, for example writeFiles: false, that agents in it cannot exceed.

Example: compiled options for an agent with only readFiles on, one connector and a read-only manuals folder (simplified)

const options = {
  settingSources: ["project"],     // the session's own project only, never host user state
  strictMcpConfig: true,  // only this agent's connectors
  allowedTools: ['mcp__<connector-name>__*'], // e.g. authority
  disallowedTools: [
    'Write', 'Edit', 'NotebookEdit',      // writeFiles off
    'Bash', 'BashOutput', 'KillShell',    // runCommands off
    'WebFetch', 'WebSearch',             // unrestrictedNetwork off
    'Write(/workspace/manuals/**)',       // read-only grant
    'Edit(/workspace/manuals/**)',
    'NotebookEdit(/workspace/manuals/**)',
  ],
  env,                    // run token, never a provider key
};

Real connector keys and workspace paths differ per run. The order and de-duplication rules are in the adapter, not shown here.

People and access

Four roles, your identity provider, and keys that do one thing.

Every member has exactly one of four roles. The roles are not a total order: an Admin has no projects grant and cannot confer the Builder role.

RoleCanCannot
ownerEverything. The only role that reads the audit trail, manages secrets and runs setup. Owns the public-sharing policy.—
adminFull control of agents, skills and files. Manages connectors, API keys, members, invitations, users, models, model connections, runtimes and shares.Projects, secrets, audit
builderReads any agent, skill, file or connector; writes and runs its own. Reads runtime profiles. Owns its own projects and sessions.Edit other people's rows; API keys, members, models, runtimes
viewerReads agents. Runs only agents it is explicitly granted. Reads its own sessions and runs.Skills, files, connectors; any ungranted agent

Single sign-on

Any OIDC issuer, set with OIDC_ISSUER_URL, OIDC_CLIENT_ID, OIDC_CLIENT_SECRET and OIDC_REDIRECT_URI. A password bootstrap admin covers first setup.

  • ✓ Entra ID
  • ✓ Okta / Cognito
  • ✓ Google

Agent Workspace is not an identity provider.

API keys

  • One fixed role per key; no finer scopes.
  • Optional expiresAt.
  • Plaintext shown once at mint; a read returns only a display prefix.
  • Refused on /api/workspaces/** and /api/invitations/**: 403 api_key_not_permitted.
  • The aw CLI never accepts a key as a flag; use --api-key-stdin.

Browser tokens

  • Scope run or session.
  • TTL 60–3600 s, default 300.
  • Stored as a hash, re-checked against the minting principal on every request.
  • Minted by your backend: aw tokens mint --scope run --id <id>.

API keys must never reach a browser.

Public surfaces

What the public can reach is explicit and narrow.

A surface is the chat page or widget visitors use. The rest of the API sends no CORS headers; a cross-origin frontend goes through your backend, or a same-origin proxy with a browser token.

Surfaces

  • allowedOrigins: up to 20 exact origins, no path, no wildcard. They set frame-ancestors and CORS on the session bootstrap and visitor run routes. No cookie is sent.
  • Any other origin gets 403 surface_origin_not_allowed.
  • Visitors are rate-limited (429 surface_rate_limited) and capped at 50 turns per conversation by default (429 surface_turn_limit_reached).
  • The origins in force are the promoted version's. A new origin needs aw promote.
  • Without allowedOrigins, the aw dev draft admits localhost and 127.0.0.1 on any port.

Shares

  • A session or project can be shared as private, workspace or public (/p/<token>). Sharing an agent or a skill is not supported today.
  • Public sharing is blocked when the workspace sharing policy is off; the policy belongs to the Owner.
  • A share is a snapshot, not a live view.
  • Expiry: 24 h, 7 days, 30 days or never. Optional passphrase, stored hashed.
  • Revoking takes effect at once.
✕ Public runnable agents are switched off today.
The runnable share mode is compiled off and refused with 400 invalid_share.

Known limits

What is not verified yet.

Read these before you plan a production rollout. Each one is stated in the product's own documentation or status records.

⚠No managed-cloud driver has a live isolation proof.
aca-sessions and cloud-run-service are implemented but not exercised by the live driver suite.
⚠kubernetes is partially verified.
Lifecycle and isolation are partially verified; no live-cluster proof has been published.
⚠stdio MCP connectors cannot run.
They are stored but cannot run today. Use http or sse.
⚠docker cannot do restricted.
Docker sandboxes are none or open; it refuses allowedDomains, and so does kubernetes.
⚠Deny-by-default networking is the design intent, not the shipped default.
The specification calls for deny by default with explicit allowlists. Set each runtime profile's policy deliberately.
⚠Not yet a declared release.
The project's release-readiness check is still red. Key backends other than Azure Key Vault, and native per-cloud stores, await live proof.

FAQ

Questions a security review asks first.

Something else? Ask us.

Can an agent read our model provider's API key?

No. Provider credentials are resolved only by the gateway. The sandbox gets a short-lived token bound to one run and one model, and the compiled run environment refuses ANTHROPIC_API_KEY.

What leaves our infrastructure?

All five services and the three stores run where you deploy them. Prompts go to the model provider you configure, through the gateway. Your own databases and document systems reach an agent only as an MCP connector or as uploaded files.

Which runtime should we use in production?

docker is the single-VM default and the only fixture-verified driver. kubernetes is implemented and partially verified. No managed-cloud driver has a live isolation proof yet. Avoid local outside development: it has no isolation.

Can we stop an agent from reaching the internet?

Yes. Set the runtime profile's network policy to none, and turn off unrestrictedNetwork so WebFetch and WebSearch are denied. A policy the driver cannot enforce is refused with 422 network_policy_not_enforceable.

How are API keys scoped and stored?

Each key carries one fixed role and an optional expiry; there are no finer scopes. The plaintext is shown once, and a read returns only a display prefix. Keys are refused on workspace and invitation routes. For browsers, mint a run or session token with a 60–3600 s lifetime instead.

Who can see the audit trail, and can we export it?

Only an Owner can read it, in the product or with aw audit list. The OpenTelemetry export covers runs (one agent.run span each), not audit rows.
