For developers and platform teams

One command to scaffold. One file to deploy. Everything else in git.

Agent Workspace is a self-hosted control plane for the Claude Agent SDK. Generate a project from a template, run it on your laptop, then ship the same images to your own cloud. Configure workspaces, skills and permissions from the browser, the aw CLI, the TypeScript SDK or YAML you commit.

Quickstart · local

From an empty folder to a running agent.

Like create-next-app: the generator writes a project you own and commit. The agent and its surface are TypeScript files, and aw dev runs them on your machine. Nothing is hidden in a hosted service.

Prerequisites: Node 24+ and npm, and an Anthropic API key in ANTHROPIC_API_KEY (and ANTHROPIC_BASE_URL if you use another endpoint) in the shell that runs aw dev; no key is written to a file. No Docker: aw dev starts the published @indx-workspace/embedded runtime with its own PostgreSQL. Agent runs use the workspace's default runtime profile local on the local driver, which has no isolation and is for development only. The runtime's Runtime: startup line names the driver it detected on the host, but runs on the local profile stay on the in-process local driver, with no isolation, whatever driver that line names.
Public registry: these four commands ship on main, and the release smoke writes the -- --yes project from the release tarballs. The public @latest (including @indx-workspace/aw, which has no init, dev, check or push on npm yet) gets them with the next package release that includes @indx-workspace/embedded. The developer-journey CI job (Journey E2E, S1-19) runs this path end to end on every push to main, from npm create answered on a terminal to the widget's answer on the try page. It does not run --yes or step 4's passing aw check; it runs aw check only to see it refuse an unsupported tool and a Viewer key. Run 37041752925, the first push to main after the job merged, took 65.1 s of its 600 s budget; run 37039234031, on the pull request that merged it, took 62.7 s. It installs packages packed from this repository from a private local registry, and the model is a stub Anthropic API, so it proves the path as main builds it, not from the public npm registry. Since slice 2 the same job also times a look change (B2) and an OpenAPI tool, written by setup (B3a) and by hand (B3b): run 37137992202, on main at d0ceb28e, took 1.0 s of 60 s for B2, and 28.0 s and 4.0 s of 900 s for B3a and B3b.
Deploying with Docker Compose instead? npm create @indx-workspace@latest acme-ai -- --cloud local writes the deployment project; see Laptop or a single VM.

  1. Scaffold the project Today

    Writes package.json (with "dev": "aw dev"), agent-workspace.yaml, one agent and one surface into a new directory, and never overwrites anything. Flags go after npm's --. Without a terminal, create refuses unless --yes (the recommended answers) or --cloud local is given. In an existing directory, npx @indx-workspace/aw init --yes writes agent-workspace.yaml, the agent and the surface; it refuses a file that exists and never edits package.json.

    shell
    npm create @indx-workspace@latest my-company-ai -- --yes

  2. Run it Today

    npm run dev runs aw dev: it starts the local runtime on environments.local.port (3000 unless the file names one), signs aw in, creates the default model connection from your key and pushes agents/ and surfaces/ to local on every save. Ctrl+C stops it.

    shell
    cd my-company-ai
npm install
npm run dev                # aw dev: ready, signed in as …, model connection, page / try / widget

  3. Open the try page and the widget Today

    Open the try: URL aw dev prints (http://127.0.0.1:3000/p/s/main/try), or paste the widget: line, a single <script> tag, into any page. Both are served by the local runtime. A message sent there runs the agent on the workspace's default runtime profile, local, which the runtime creates at start, with the default model connection. The generated agent names no model id (model: 'default'), so the run uses the deployment default model the local runtime sets: claude-sonnet-4-5 for Anthropic, or its newest dated release.

  4. Check, then save a version Today

    In a second terminal inside the project, aw finds the local URL in agent-workspace.yaml and the key aw dev stored, so it needs no login. aw check reports problems and saves nothing; aw push shows the diff, and only --yes saves a version per agent and points local at it.

    shell
    npx aw check
npx aw push                # shows the diff, saves nothing
npx aw push --yes --summary "First version"

  5. Turn an internal API into a tool Today

    Answer openapi to the internal-tools question in npm create, or write tools/orders.ts with openapiTool() and import it into the agent. The credential is a secret() name that aw dev reads from its environment; aw dev registers the tool, and the gateway calls the API, so you run no MCP server. Only GET and HEAD operations are allowed. The docs' "Tools from code" guide has the rules.

    shell
    export ORDERS_TOKEN=…      # the API's credential, never in a file
npm run dev                # aw dev registers tools/orders.ts, then syncs the agent
Project layout

What the template puts on disk.

Everything above workspace/ is generated today: the default project by npm create @indx-workspace@latest <dir> -- --yes, the rows marked --cloud … by the deployment project. The workspace/ folder is the proposed home for workspace settings an admin clicks in the browser.

Commit agent-workspace.yaml, agents/ and surfaces/. Never commit .env: in a deployment project it holds the generated admin password and store credentials. Both generated .gitignore files already exclude it; the default one also excludes the local runtime's .agent-workspace/.
Rendered files under deploy/ are outputs. Change the profile and re-render instead of editing them, so nothing is configured twice.
my-company-ai/

│                                  # --cloud …: deployment profile: cloud, stores, runtime, identity
├─ agents/assistant.ts    today    # default: the agent as code (defineAgent)
├─ surfaces/main.ts       today    # default: page, try page and widget (defineSurface)

Configuration as code

Two files decide a deployment. A folder decides a workspace.

Keep the layers apart. The deployment profile says where state lives and is read by the installer. The workspace folder says what the people and agents inside one workspace can do and is applied through the public API, the same API the browser uses.

1. Deployment profile Today

The only place the five infrastructure decisions are written: relational store, object store, secret store, default sandbox, identity. Validated before any file is written; --validate also probes each store whose credential is present.

The grammar is a deliberate subset: two levels of string scalars, no lists, anchors or block scalars. Anything else is refused by line number (ADR-0055).

shell
npx -p @indx-workspace/cli agent-workspace validate acme-ai
agent-workspace.yaml
cloud: gcp
storage:
  relational: cloud-sql            # or a postgres:// URL; the credential stays in .env
  objects: gcs://acme-ai-files     # s3:// | gcs:// | azblob:// | local-filesystem
  secrets: secret-manager          # local-key | kms | secret-manager | key-vault
runtime:
  default: cloud-run-service      # docker | kubernetes | aca-sessions | sandbox-runtime …
identity:
  oidc: https://accounts.google.com
  bootstrapAdmin: ops@acme.example

2. Workspace definition Proposed

One YAML file per resource, in the folder layout above. aw plan prints a diff against the live workspace; aw apply sends only the difference through the SDK; aw pull exports a workspace someone configured in the browser into files.

Credentials never appear in these files. A connection names a secret with secretRef, and the value goes in through aw secrets create --value-stdin.

Needs a real YAML parser (the ADR-0055 exit, separate from the profile reader), agent export and import (roadmap K-1), and a delete route for skills and secrets (S-12, S-10) before apply can remove what a file no longer names.

shell · proposed
aw pull  ./workspace            # export what exists
aw plan  ./workspace            # + agent support-desk   ~ skill release-notes (enabled)
aw apply ./workspace --yes      # run in CI after merge

Skills

A skill is a folder. Keep it that way.

Author a standard Claude SKILL.md directory in any editor. The platform stores it, exports it byte for byte, and places it in the run's sandbox. You never write to the sandbox path yourself.

Portable. The same folder works in Claude Code and in a plain Agent SDK app. Workspace-only metadata goes in the proposed skill.yaml beside it, never inside SKILL.md.
Not yet. aw skills remove waits on a server route (S-12). Disable a skill instead of deleting it.

---
name: release-notes
description: Draft release notes from merged pull requests.
allowed-tools: Read, Grep
---

Deploy

Local first, then the environment you are given.

One image set everywhere. Cloud differences live in two places only: the container registry and the runtime driver. Both are configuration in agent-workspace.yaml.

--cloud is required for a deployment project: without it, create writes the aw dev project. Each image is pinned to a registry digest before anything is written, and generation fails if an image cannot be verified. pnpm start checks the digests, starts web, runner, gateway, PostgreSQL and object storage, and prints the configured and effective runtime. Open the URL it prints (http://localhost:3000/setup on a local Docker) and sign in with the administrator email and the “One-time setup password” the generator printed. The setup wizard tests the model provider key first, then asks for the runtime, the first administrator and the first agent. Mint an API key under Administration → API Keys (/admin/api-keys) to point aw at it.

Automate

The same calls from your app and from CI.

Every aw command is one SDK method. A key never travels as a flag: --api-key is refused, so use --api-key-stdin, the environment, or a profile that names an environment variable.

~/.config/agent-workspace/profiles.json
{
  "default": { "url": "https://aw.acme.example",  "apiKeyRef": "AW_PROD_KEY" },
  "staging": { "url": "https://aw-stg.acme.example", "apiKeyRef": "AW_STAGING_KEY" }
}
run-agent.ts
import { createClient } from '@indx-workspace/sdk';

const aw = createClient({
  baseUrl: process.env.AGENT_WORKSPACE_URL!,
  auth: { kind: 'api-key', apiKey: process.env.AGENT_WORKSPACE_API_KEY! },
});

const { run } = await aw.runs.start(agentId, {
  prompt: 'Summarise the open incidents.',
});
for await (const frame of aw.runs.follow(run.id)) {
  if (frame.kind === 'run-status') console.log(frame.data.status);
}

Edit the codebase

Fork it, change it, keep the gates green.

A pnpm monorepo in strict TypeScript. Contracts come first; the SDK, the CLI and the server all depend on them, never the other way round.

shell
git clone <your fork> agent-workspace && cd agent-workspace
pnpm install
pnpm build                 # build first; tests import dist
pnpm check:fast            # lint, types, format, docs
pnpm test                  # provisions throwaway databases in Docker

packages/awThe operator CLI, one command per SDK methoda method needs a command
packages/cliThe deployment generator: create-agent-workspace, start, validatea new cloud, store or template file
packages/runtimeRuntime drivers: docker, kubernetes, cloud-run-service, aca-sessions …a new sandbox
packages/gatewayModel gateway that keeps provider keys off the sandboxa new model provider

Add a runtime driver

Implement the driver interface in packages/runtime, register its id in the contracts, pass the conformance suite.

Add a model provider

Write an adapter behind the gateway. The provider key stays in the gateway; runs receive a scoped token.

Add an engine

Implement the engine port and emit the neutral agent.* events. The platform supplies credentials, file grants and skills.

Add an API route

Contract first: schema in contracts, handler in apps/web, method in sdk, command in aw, docs regenerated.

Roadmap

Generate once, then keep upgrading. Five phases get there.

Ordered by dependency. Every write surface ships its read-only form first, and every phase works on --cloud local before any cloud. Each phase has exit criteria and open decisions.

  1. Phase 0 · Make the boilerplate installable

    Publish the project CLI to npm under @indx-workspace (@indx-workspace/aw, the SDK and the contracts publish from packages-v* tags since #246), refuse version skew by name. Exit: npm create @indx-workspace@latest demo works from the public registry (met with 0.1.0; 0.2.x is @latest now). On main, create without --cloud writes the aw dev project and, without a terminal, needs -- --yes; -- --cloud local writes the Compose project.

  2. Phase 1 · Profile v1 and the render / deploy loop

    Real YAML with apiVersion, JSON Schema for editors, render, plan-first deploy over Compose, Helm and Terraform, doctor.

  3. Phase 2 · Workspace as code

    Server prerequisites first (K-1, S-10, S-12, S-20, S-22), then pull → plan → apply → apply --prune, and a plan-on-PR workflow. For agents this is superseded by the developer journey: agents go through versions, with aw push today and aw pull in slice 2; where workspace settings live is decided in its own ADR.

  4. Phase 3 · The upgrade loop

    Signed release manifest, agent-workspace upgrade with file codemods and a deploy plan. Exit: two minor releases with no manual edit.

  5. Phase 4 · Extensions without a fork

    @agent-workspace/testkit, define* helpers for storage, secrets, runtimes, models and engines, extensions/ baked in by agent-workspace build. SQL stays Postgres-compatible; an extension may keep its own tables in a dedicated ext_<name> schema.

  6. Phase 5 · Templates and ecosystem

    --template minimal | team | enterprise, skill and agent packs, a gallery where CI boots every template.
